# todo-orchestrator

계획 세션을 처음부터 끝까지 잇는다: 계획 요청 → 후보 조회 → 체크박스 선택 → Discord 오늘작업 원본 생성·수정 → 결과 안내. 사용자가 항목을 고른 뒤 전송 스킬을 다시 부르지 않아도 되도록 Discord 기록까지 이 스킬이 진행한다.

Issue 본문은 읽지 않는다. 후보는 제목, 라벨, 담당자, 연결 PR, GitHub Relationships만으로 분류한다. 관계는 `docs/git/issue.md`의 "관계"에 따라 Relationships에만 있으므로 본문을 읽지 않아도 막힘을 판정할 수 있고, 같은 Issue 상태면 같은 후보가 나온다. 분류 기준은 `references/classification.md`에만 둔다.

## 범위

이 스킬은 사용자 요청을 LLM이 해석해 따르는 지침이다. 훅·예약 실행·상태 머신이 강제하는 자동화가 아니므로 "자동 실행"이라고 설명하지 않는다.

- Issue를 생성·수정·종료하지 않는다.
- 오늘 목록 선택·변경은 코딩 시작이나 진행 중 작업 중단 지시가 아니다.
- 오늘 목록 본문은 Discord에만 둔다. 날짜별 Issue·Markdown 일지·DB를 만들지 않는다.
- 다음 날 목록은 사용자 선택을 받아 새 원본으로 만든다. 미완료 작업을 자동으로 넘기지 않는다.

## 작업 목록

0단계에서 요청 종류를 정하면 바로 `TaskCreate`로 그 종류가 거칠 단계를 작업 하나씩 만든다. 제목은 `N단계: <단계 이름>`이다. 남은 단계가 목록에 보여야 원본 확인 같은 단계를 건너뛰지 않는다.

- 단계를 시작할 때 `TaskUpdate`로 `in_progress`, 끝나면 `completed`로 바꾼다. 한 번에 하나만 `in_progress`다.
- 요청 종류가 거치지 않는 단계는 만들지 않는다. 예: 후보만은 0~3단계, 목록 변경은 0·1·2·4·5단계만 만든다. 0단계 작업은 만들자마자 `in_progress`다.
- 사용자가 아무것도 고르지 않았거나 오류로 멈추면 남은 작업을 `completed`로 바꾸지 않는다. 5단계 안내에 멈춘 단계를 쓴다.
- 작업 목록은 이 세션 안의 진행 표시다. 오늘 목록의 원본은 Discord다.

## 0단계: 맥락·기존 작업 확인

1. **저장소**: 요청에 `owner/repo`가 있으면 그것, 없으면 `git remote get-url origin`에서 구한다. 다른 저장소는 사용자가 명시했을 때만 넣는다. 저장소마다 아래 단계를 따로 진행하고 원본도 따로 둔다.
2. **날짜**: `TZ=Asia/Seoul date +%F`.
3. **요청 종류**를 정한다. 모호하면 이것만 묻는다.

   | 종류           | 신호                         | 진행할 단계                                           |
   | -------------- | ---------------------------- | ----------------------------------------------------- |
   | 후보만         | "후보 보여줘", "뭐 있는지만" | 1·2, 3단계의 터미널 목록까지. Discord에 보내지 않는다 |
   | 첫 계획        | "오늘 계획 세워줘"           | 0~5 전부                                              |
   | 목록 직접 지정 | "#21, #23 올려줘"            | 1·2 후 체크박스 없이 지정 Issue로 4·5                 |
   | 목록 변경      | "추가", "빼줘"               | 1·2 후 체크박스 없이 4·5                              |

   지정 Issue가 1단계 결과에 없으면(닫힘, 없는 번호) 목록에 넣기 전에 알린다.

4. **채널과 오늘 원본**: Discord 단계가 있는 요청이면 후보 조회 전에 `.claude/skills/discord-message/references/tools.md`(이하 `tools.md`)의 "도구 준비", "대상 채널", "기록 조회"를 따른다. 원본 상태를 셋 중 하나로 판정해 둔다.
   - **있음(1개)**: 메시지 ID와 현재 목록을 기억한다.
   - **없음 확정**: 조회 결과가 100개 미만이거나, 가장 오래된 메시지가 오늘 KST 0시보다 이전이다. 조회 결과의 시각은 UTC이므로 KST 0시는 UTC 전날 15:00로 바꿔 비교한다. 즉 오늘 범위를 모두 봤다.
   - **판정 불가**: 오늘 범위를 다 보지 못했는데 못 찾음, 여러 개 나옴, 도구 연결 안 됨. 추측하지 않는다. 4단계에서 사용자에게 확인한다.

## 1단계: 조회

열린 Issue 전체를 GraphQL 한 번으로 읽는다. GitHub MCP에는 blocked by와 연결 PR을 한 번에 읽는 조회가 없어 `gh`를 쓴다.

```sh
gh api graphql -f owner=<owner> -f repo=<repo> -f query='
query($owner:String!,$repo:String!,$after:String){ repository(owner:$owner,name:$repo){
  issues(states:OPEN, first:100, after:$after){ totalCount pageInfo{hasNextPage endCursor} nodes{
    number title url updatedAt
    labels(first:10){nodes{name}}
    assignees(first:5){nodes{login}}
    parent{number}
    subIssues(first:50){nodes{number state}}
    blockedBy(first:20){nodes{number state}}
    blocking(first:20){nodes{number state}}
    closedByPullRequestsReferences(first:5, includeClosedPrs:true){nodes{number state}}
}}}}'
```

`hasNextPage`가 참이면 `-f after=<endCursor>`로 끝까지 넘긴다. 가져온 수와 `totalCount`를 비교한다. 다르거나 호출이 실패하면 "일부 조회(n/N)" 또는 "조회 실패"로 기록하고, 이후 어디에서도 "전체 후보"라고 하지 않는다.

## 2단계: 분류

`references/classification.md`로 Issue마다 상태, 카테고리, 관계 안내를 정한다. 상위 묶음은 후보에서 뺀다.

## 3단계: 사용자 선택 (체크박스)

1. 터미널에 조회 범위와 카테고리별 후보 목록을 먼저 보여준다. 형식은 `formats.md` "오늘작업"과 같고, 항목마다 상태를 붙인다. 넘친 후보(아래 3)와 상위 묶음은 번호와 제목만 따로 쓴다.
2. "후보만" 요청이면 여기서 끝낸다. 오늘 목록을 기록하려면 "오늘 계획 세워줘"로 다시 요청하라고 한 줄로 안내한다.
3. `AskUserQuestion`을 `multiSelect: true`로 한 번 호출한다. 질문은 카테고리 하나에 하나, 선택지는 `classification.md` "체크박스 구성"을 따른다. 도구 상한은 질문 4개, 질문당 선택지 4개다.
4. 고른 항목과 "Other"에 적은 번호를 합친다. Other의 번호가 1단계 결과에 없거나 상위 묶음이면 무엇이 문제인지 알리고 다시 묻는다.
5. 아무것도 고르지 않았으면 기록하지 않고 끝낸다.
6. 막힌 Issue를 골라도 막지 않는다. 선택은 사용자의 권한이다. 결과에 막힘 안내가 붙는다.
7. 이 단계까지는 Discord에 아무것도 보내지 않는다.

## 4단계: Discord 오늘작업 원본 기록

새 목록 본문을 `.claude/skills/discord-message/references/formats.md`의 "공통 규칙"과 "오늘작업" 형식으로 만든다. 항목 순서는 `classification.md` "결과 순서"를 따른다. 목록 변경 요청이면 원본의 현재 항목에 요청한 추가·제외만 반영하고, 막힘 안내와 순서는 1단계 조회로 다시 계산한다. 수정은 메시지 전체를 바꾸므로 빠진 항목이 없는지 확인한다.

| 0단계 원본 상태      | 할 일                                                                                                                                                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 있음, 새 본문과 같음 | 보내지 않는다. 기존 원본 ID를 안내한다                                                                                                                                                        |
| 있음, 다름           | `tools.md` "수정"으로 기존 원본을 고친다                                                                                                                                                      |
| 없음 확정            | `tools.md` "전송"으로 새 원본을 보낸다. 목록 변경 요청이었다면 고칠 원본이 없다고 알리고 새로 만들지 묻는다                                                                                   |
| 판정 불가            | 보내지 않는다. 이유를 알리고 오늘 원본이 있는지 묻는다. 사용자가 메시지 ID를 주면 그 메시지 내용을 확인할 수 없으므로 현재 목록 전체를 확인받은 뒤 수정한다. 사용자가 없다고 하면 새로 보낸다 |

성공 여부는 도구의 성공 응답으로만 판정한다. 실패·부분 전송·응답 없음은 `tools.md` "실패 처리"를 따르고 무조건 재시도하지 않는다.

## 5단계: 결과 안내

- **성공**: 대화창에 Discord로 보낸 본문과 같은 오늘작업 목록을 그대로 보여주고, "계획 기록 완료", 원본 메시지 ID, 생성·수정·변경 없음 중 무엇이었는지를 알린다. 코딩은 새 세션에서 Issue 링크로 따로 시작하라고 한 줄 덧붙인다.
- **선행 누락**: 고른 막힌 Issue의 실제 선행(`classification.md` "실제 선행")이 오늘 목록에 없으면 성공·실패와 함께 `#27의 선행 #29가 오늘 목록에 없음`처럼 한 줄씩 알린다. 선택을 바꾸라고 하지 않는다.
- **실패·불확실**: 같은 목록을 대화창에 보여주고 "기록 미완료"와 이유를 알린다. 메시지 ID를 지어내지 않는다. 코딩을 시작하지 않는다.

여기서 계획 세션은 끝난다.

## 오류 처리

| 상황                       | 할 일                                        |
| -------------------------- | -------------------------------------------- |
| GitHub 인증 만료·권한 거부 | 재시도하지 않는다. 오류 문구를 알리고 멈춘다 |

## 테스트 시나리오

### 정상 흐름

1. **첫 계획(정상)**: "오늘 계획 세워줘" → GraphQL 조회 → 분류 → 터미널 목록 → 카테고리별 체크박스 → 사용자가 고름 → 원본 없음 확정 → 새 전송 → 대화창에 같은 목록과 메시지 ID.
2. **목록 변경**: 같은 날 "#23 추가하고 #24 빼줘" → 조회 → 원본 1개 찾음 → 항목 반영, 순서·막힘 안내 재계산 → 수정 → 같은 ID 안내.
3. **같은 요청 반복**: 같은 날 같은 목록으로 다시 요청 → 원본과 같음 → 전송하지 않음.
4. **후보만**: "오늘 할 이슈 후보만 보여줘" → 터미널 목록 후 종료. 체크박스·Discord 호출 없음.
5. **카테고리 넘침**: feature 후보가 6건 → 체크박스에 4건, 나머지 2건은 터미널에 번호만 → Other에 번호 입력으로 선택 가능.
6. **막힌 Issue 선택**: #24(blocked by #22)를 고름 → 막지 않음 → 결과에 `← #22`와 `#24의 선행 #22가 오늘 목록에 없음`.
7. **상위 묶음**: #21(열린 하위 있음) → 체크박스에 없음, 터미널에 번호와 제목만.
8. **상위 묶음이 선행**: #27(blocked by #19), #19의 열린 하위는 #29 → #27 아래에 `← #19`, 그 다음 줄에 두 칸 더 들여 `└─ #29 남음`. 체크박스의 #29 설명에는 `🔓 끝내면 #27 시작 가능 (#19 닫은 뒤)`를 쓰되 Discord 메시지에는 반복하지 않는다. 둘 다 고르면 #29가 먼저.
9. **분류 경계**: blocked by가 열려 있으면 막힘, 본문에만 적힌 의존은 막힘이 아님. 커밋에 `Refs #N`만 적은 PR은 연결 PR이 아니라 진행 중 근거가 되지 않음.

### 오류 흐름

1. **원본 판정 불가**: 최근 100개가 모두 오늘 메시지인데 원본이 없음 → 보내지 않고 사용자에게 원본 여부 확인.
2. **전송 실패**: 응답이 `reply failed: channel not allowlisted` → 재시도하지 않음 → 오류 문구와 `/discord:access` 안내 → 대화창에 목록과 "기록 미완료".
3. **GitHub 인증 만료**: GraphQL 조회가 권한 오류 → 재시도하지 않고 오류 문구를 알린 뒤 멈춤. Discord 호출 없음.
4. **아무것도 고르지 않음**: 체크박스에서 선택 없음 → 기록하지 않고 종료. 4·5단계 작업은 `completed`로 바꾸지 않음.
