# todo-orchestrator

계획 세션을 처음부터 끝까지 잇는다: 계획 요청 → 후보 조회 → 사용자 선택 → Discord 오늘작업 원본 생성·수정 → 결과 안내. 사용자가 항목을 고른 뒤 전송 스킬을 다시 부르지 않아도 되도록 Discord 기록까지 이 스킬이 진행한다.

## 실행 모드: 서브에이전트 위임

메인 세션이 흐름을 이끌고, Issue 본문을 읽는 3단계 분류만 서브에이전트에 한 번 맡긴다. 서브에이전트는 사용자에게 묻지 못하고 Discord 결과는 사용자 안내와 바로 이어져야 하므로, 질문·Discord 호출·최종 판정은 메인이 한다. 토큰은 대부분 본문을 읽는 데서 나가므로 본문은 좁힌 Issue만, 한 번만 읽는다.

| 에이전트 | `subagent_type`            | 호출                            | 모델                                                 | 입력                                                                                       | 산출물                           |
| -------- | -------------------------- | ------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------- |
| analyst  | `oh-my-claudecode:analyst` | 3단계, 단발(`name` 없음), 한 번 | `opus`. 선행 관계·정의 상태를 본문에서 판단해야 한다 | `references/prompts.md` 프롬프트(1단계 목록, 상세 대상 번호, 하루 작업량, 사용자 우선순위) | 반환 메시지(Markdown). 파일 없음 |

하네스 기본 구성과 다르게 둔 것과 이유:

- `.claude/agents/`에 정의 파일을 두지 않고 oh-my-claudecode 에이전트를 쓴다. 이미 설치된 전문 에이전트를 재사용하기로 했다.
- `_workspace/`를 만들지 않는다. 계획 세션은 Discord 기록 뒤 끝나고, 남길 기록은 GitHub Issue와 Discord에 있다.
- 검증 에이전트를 두지 않는다. 4단계 참고.

GitHub 조회는 GitHub MCP 도구(`list_issues`, `issue_read`)를 쓴다. 지연 로드 목록에만 있으면 `ToolSearch`로 불러온다. MCP가 없을 때만 `gh` CLI를 쓰고, 그 사실을 결과에 적는다.

## 범위

이 스킬은 사용자 요청을 LLM이 해석해 따르는 지침이다. 훅·예약 실행·상태 머신이 강제하는 자동화가 아니므로 "자동 실행"이라고 설명하지 않는다.

- Issue를 생성·수정·종료하지 않는다. 정의가 부족해도 표시만 한다.
- 오늘 목록 선택·변경은 코딩 시작이나 진행 중 작업 중단 지시가 아니다.
- 오늘 목록 본문은 Discord에만 둔다. 날짜별 Issue·Markdown 일지·DB를 만들지 않는다.
- 다음 날 목록은 사용자 선택을 받아 새 원본으로 만든다. 미완료 작업을 자동으로 넘기지 않는다.

## 0단계: 맥락·기존 작업 확인

1. **저장소**: 요청에 `owner/repo`가 있으면 그것, 없으면 `git remote get-url origin`에서 구한다. 다른 저장소는 사용자가 명시했을 때만 넣는다. 저장소마다 아래 단계를 따로 진행하고 원본도 따로 둔다.
2. **날짜**: `TZ=Asia/Seoul date +%F`.
3. **하루 작업량**: 기본 6시간. "오늘 4시간"처럼 말하면 그 값.
4. **요청 종류**를 정한다. 모호하면 이것만 묻는다.

   | 종류           | 신호                         | 진행할 단계                                    |
   | -------------- | ---------------------------- | ---------------------------------------------- |
   | 후보만         | "후보 보여줘", "뭐 있는지만" | 1~5에서 후보 제시까지. Discord에 보내지 않는다 |
   | 첫 계획        | "오늘 계획 세워줘"           | 0~7 전부                                       |
   | 목록 직접 지정 | "#21, #23 올려줘"            | 1~4 대신 지정 Issue 확인, 5~7                  |
   | 목록 변경      | "추가", "빼줘", "순서"       | 지정 Issue 확인, 6·7                           |

   지정 Issue 확인: 번호마다 `issue_read` `get`으로 존재·열림·제목·링크를 확인한다. 닫혔거나 없으면 목록에 넣기 전에 알린다.

5. **채널과 오늘 원본**: Discord 단계가 있는 요청이면 후보 조회 전에 `.claude/skills/discord-message/references/tools.md`(이하 `tools.md`)의 "도구 준비", "대상 채널", "기록 조회"를 따른다. 원본 상태를 셋 중 하나로 판정해 둔다.
   - **있음(1개)**: 메시지 ID와 현재 목록을 기억한다.
   - **없음 확정**: 조회 결과가 100개 미만이거나, 가장 오래된 메시지가 오늘 KST 0시보다 이전이다. 조회 결과의 시각은 UTC이므로 KST 0시는 UTC 전날 15:00로 바꿔 비교한다. 즉 오늘 범위를 모두 봤다.
   - **판정 불가**: 오늘 범위를 다 보지 못했는데 못 찾음, 여러 개 나옴, 도구 연결 안 됨. 추측하지 않는다. 6단계에서 사용자에게 확인한다.

## 1단계: 전체 목록

`list_issues`를 `state: OPEN`, `fields: [number, title, labels, assignees, updated_at]`, `orderBy: UPDATED_AT`, `direction: DESC`, `perPage: 100`으로 호출한다. `hasNextPage`가 참이면 `after`로 끝까지 넘긴다.

가져온 수와 `totalCount`를 비교한다. 다르거나 호출이 실패하면 "일부 조회(n/N)" 또는 "조회 실패"로 기록하고, 이후 어디에서도 "전체 후보"라고 하지 않는다. 본문은 이 단계에서 읽지 않는다.

## 2단계: 좁히기

본문 없이 1단계 정보만으로 상세 검토 대상을 **최대 10건** 고른다. 하루 작업은 몇 건 수준이라 10건이면 고를 여유가 있고, 더 읽으면 비용만 늘어난다.

1. 사용자가 지정한 Issue
2. 담당자가 있는 Issue
3. 최근 갱신순

상위 이슈인지는 이 단계에서 알 수 없다. 3단계에서 analyst가 확인하고 하위로 대체한다. 고르지 않은 Issue는 "상세 미검토"로 남아 제목만 보인다. 사용자가 그중 하나를 지정하면 다음 실행에서 상세 대상에 반드시 넣는다.

## 3단계: 상세 분류 (analyst)

`references/prompts.md`의 analyst 프롬프트를 채워 `Agent(subagent_type: "oh-my-claudecode:analyst", model: "opus")`로 호출한다. `name`은 주지 않는다. 1단계 목록은 프롬프트에 그대로 넣고, 본문은 analyst가 직접 읽는다. 메인이 본문을 읽어 넘기면 같은 본문을 두 번 읽게 된다.

## 4단계: 확인 (메인)

별도 검증 에이전트를 두지 않는다. 후보는 제안이고 최종 선택은 사용자가 하므로, 메인이 다음만 확인한다.

- 오늘 후보마다 근거 인용이 있고, 분류가 `references/classification.md`의 뜻과 맞는지 analyst 출력으로 본다.
- 열린 Issue 전체가 한 번씩 분류됐는지(1단계 목록과 대조), 상위·하위를 두 번 세지 않았는지 본다.
- 의심스러운 항목만 `issue_read`로 직접 연다. 전체를 다시 읽지 않는다.

## 5단계: 사용자 선택

1. 터미널에 이 순서로 보여준다: 조회 범위 → 오늘 후보(선정 이유·현재 상태·다음 행동·끝내면 풀리는 Issue를 한 줄씩) → 그 외 시작 가능 → 따로 표시(분류별) → 상세 미검토 → 묶음.
2. 이 단계에서는 Discord에 아무것도 보내지 않는다. 후보는 확정 목록이 아니다.
3. "후보만" 요청이면 여기서 끝낸다. 오늘 목록을 기록하려면 고를 Issue를 알려 달라고 한 줄로 안내한다.
4. 사용자가 고른 Issue를 순서대로 정리한다. 상위 이슈를 고르면 하위 중 무엇을 할지, 번호가 모호하면 어느 것인지만 묻는다. 정의 필요 Issue를 고르면 그대로 넣되 목록에 `(정의 필요)`를 붙인다. 하루 작업량보다 많이 골라도 막지 않는다. 선택은 사용자의 권한이다.

## 6단계: Discord 오늘작업 원본 기록

새 목록 본문을 `.claude/skills/discord-message/references/formats.md`의 "공통 규칙"과 "오늘작업" 형식으로 만든다. 첫 줄은 `## 📋 오늘작업 · <repo> · <날짜> KST`(owner 제외)이고 항목 순서는 사용자가 정한 순서다. 목록 변경 요청이면 원본의 현재 목록에 요청한 추가·제외·순서 변경만 반영한다. 수정은 메시지 전체를 바꾸므로 빠진 항목이 없는지 확인한다.

| 0단계 원본 상태      | 할 일                                                                                                                                                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 있음, 새 본문과 같음 | 보내지 않는다. 기존 원본 ID를 안내한다                                                                                                                                                        |
| 있음, 다름           | `tools.md` "수정"으로 기존 원본을 고친다                                                                                                                                                      |
| 없음 확정            | `tools.md` "전송"으로 새 원본을 보낸다. 목록 변경 요청이었다면 고칠 원본이 없다고 알리고 새로 만들지 묻는다                                                                                   |
| 판정 불가            | 보내지 않는다. 이유를 알리고 오늘 원본이 있는지 묻는다. 사용자가 메시지 ID를 주면 그 메시지 내용을 확인할 수 없으므로 현재 목록 전체를 확인받은 뒤 수정한다. 사용자가 없다고 하면 새로 보낸다 |

성공 여부는 도구의 성공 응답으로만 판정한다. 실패·부분 전송·응답 없음은 `tools.md` "실패 처리"를 따르고 무조건 재시도하지 않는다.

## 7단계: 결과 안내

- **성공**: "계획 기록 완료"와 함께 날짜, 저장소, 선택한 Issue 링크(순서대로), 원본 메시지 ID, 생성·수정·변경 없음 중 무엇이었는지를 알린다. 코딩은 새 세션에서 Issue 링크로 따로 시작하라고 한 줄 덧붙인다.
- **실패·불확실**: 선택한 목록은 그대로 터미널에 보여주고 "기록 미완료"와 이유를 알린다. 메시지 ID를 지어내지 않는다. 코딩을 시작하지 않는다.

여기서 계획 세션은 끝난다.

## 오류 처리

| 상황                       | 할 일                                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GitHub 인증 만료·권한 거부 | 재시도하지 않는다. 오류 문구를 알리고 멈춘다                                                                        |
| analyst 실패               | 한 번 다시 호출한다. 또 실패하면 메인이 상세 대상을 직접 읽어 분류하고 "에이전트 분류 실패, 메인 분류"라고 표시한다 |

## 테스트 시나리오

### 정상 흐름

1. **첫 계획(정상)**: "오늘 계획 세워줘" → 전체 목록 → 10건 이하로 좁힘 → analyst → 메인 확인 → 후보 제시 → 사용자가 고름 → 원본 없음 확정 → 새 전송 → 메시지 ID 안내.
2. **목록 변경**: 같은 날 "#23 추가하고 #24 빼줘" → 지정 Issue 확인 → 원본 1개 찾음 → 기존 목록에 반영 → 수정 → 같은 ID 안내.
3. **같은 요청 반복**: 같은 날 같은 목록으로 다시 요청 → 원본과 같음 → 전송하지 않음.
4. **후보만**: "오늘 할 이슈 후보만 보여줘" → 5단계 제시 후 종료, Discord 호출 없음.
5. **상한 초과**: 열린 Issue가 10건을 넘음 → 상세 10건만, 나머지는 "상세 미검토"로 제목만.
6. **작업량 지정**: "오늘 3시간만" → 후보를 그만큼 줄이고 나머지는 "그 외"로.
7. **상위 이슈가 좁히기에 들어옴**: analyst가 하위로 대체하고 상위 본문은 근거로만 읽음.
8. **분류 경계**: 명시 선행이 열린 Issue는 막힘, 추정 선행만 있으면 막힘이 아님, 사용자 결정이 남은 Issue는 판단 대기.

### 오류 흐름

1. **원본 판정 불가**: 최근 100개가 모두 오늘 메시지인데 원본이 없음 → 보내지 않고 사용자에게 원본 여부 확인.
2. **전송 실패**: 응답이 `reply failed: channel not allowlisted` → 재시도하지 않음 → 오류 문구와 `/discord:access` 안내 → 선택 목록과 "기록 미완료" 안내.
3. **GitHub 인증 만료**: `list_issues`가 권한 오류 → 재시도하지 않고 오류 문구를 알린 뒤 멈춤. Discord 호출 없음.
4. **analyst 실패**: 한 번 다시 호출 → 또 실패 → 메인이 상세 대상을 직접 읽어 분류하고 "에이전트 분류 실패, 메인 분류"를 표시.
