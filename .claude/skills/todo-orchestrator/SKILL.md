# todo-orchestrator

계획 세션을 처음부터 끝까지 잇는다: 계획 요청 → 후보 조회 → 체크박스 선택 → 상태 라벨 기록 → Discord 알림 → 결과 안내. 사용자가 항목을 고른 뒤 다른 스킬을 다시 부르지 않아도 되도록 기록과 알림까지 이 스킬이 진행한다.

Issue 본문은 읽지 않는다. 후보는 제목, 라벨, GitHub Relationships만으로 분류한다. 관계는 `docs/git/issue.md`의 "관계"에 따라 Relationships에만 있으므로 본문을 읽지 않아도 막힘을 판정할 수 있고, 같은 Issue 상태면 같은 후보가 나온다. 상태 라벨과 분류 기준은 `references/classification.md`에만 둔다.

## 범위

이 스킬은 사용자 요청을 LLM이 해석해 따르는 지침이다. 훅·예약 실행·상태 머신이 강제하는 자동화가 아니므로 "자동 실행"이라고 설명하지 않는다.

- 오늘 목록의 원본은 Issue의 상태 라벨이다(`classification.md` "상태 라벨"). Discord 메시지는 알림이며, 다시 읽어 판단에 쓰지 않는다. 날짜별 Issue·Markdown 일지·DB를 만들지 않는다.
- Issue에서 바꾸는 것은 `SELECTED` 라벨을 붙이고 떼는 것뿐이다. 제목·본문·열림·닫힘·관계·종류 라벨은 바꾸지 않는다. `IN_PROGRESS`도 붙이거나 떼지 않는다. 작업 시작은 이 스킬의 범위가 아니다.
- 오늘 목록 선택·변경은 코딩 시작이나 진행 중 작업 중단 지시가 아니다.
- 날짜가 바뀌어도 라벨을 정리하지 않는다. 오늘 목록은 상태 라벨이 붙은 열린 Issue 전체다.

## 작업 목록

0단계에서 요청 종류를 정하면 바로 `TaskCreate`로 그 종류가 거칠 단계를 작업 하나씩 만든다. 제목은 `N단계: <단계 이름>`이다. 남은 단계가 목록에 보여야 재조회 같은 단계를 건너뛰지 않는다.

- 단계를 시작할 때 `TaskUpdate`로 `in_progress`, 끝나면 `completed`로 바꾼다. 한 번에 하나만 `in_progress`다.
- 요청 종류가 거치지 않는 단계는 만들지 않는다. 예: 후보만은 0~3단계, 직접 지정·제외는 0·1·2·4·5·6단계만 만든다. 0단계 작업은 만들자마자 `in_progress`다.
- 사용자가 아무것도 고르지 않았거나 오류로 멈추면 남은 작업을 `completed`로 바꾸지 않는다. 6단계 안내에 멈춘 단계를 쓴다.
- 작업 목록은 이 세션 안의 진행 표시다. 오늘 목록의 원본은 상태 라벨이다.

## 0단계: 맥락 확인

1. **저장소**: 요청에 `owner/repo`가 있으면 그것, 없으면 `git remote get-url origin`에서 구한다. 다른 저장소는 사용자가 명시했을 때만 넣는다. 저장소마다 아래 단계를 따로 진행한다.
2. **날짜**: `TZ=Asia/Seoul date +%F`. 알림 제목 줄에만 쓴다.
3. **요청 종류**를 정한다. 모호하면 이것만 묻는다. Issue 번호를 말했지만 오늘 목록에 넣으라는 뜻인지 분명하지 않으면(예: "chore 이슈를 다룰 거야") 기록하기 전에 묻는다.

   | 종류      | 신호                                             | 진행할 단계                                  |
   | --------- | ------------------------------------------------ | -------------------------------------------- |
   | 후보만    | "후보 보여줘", "열린 이슈 구분해서", "뭐 있는지" | 1·2, 3단계의 터미널 목록까지. 라벨·알림 없음 |
   | 추가 선택 | "오늘 계획 세워줘", "뭐 할지 골라줘"             | 0~6 전부                                     |
   | 직접 지정 | "#21, #23 올려줘", "오늘은 #27 할게"             | 1·2 후 체크박스 없이 지정 Issue로 4~6        |
   | 제외      | "#22 빼줘"                                       | 1·2 후 4~6. 체크박스로 제외하지 않는다       |

4. **라벨 존재**: 라벨 기록이 있는 요청이면 `gh label list --search SELECTED`와 `--search IN_PROGRESS`로 두 라벨이 저장소에 있는지 확인한다. 없으면 만들지 않고 멈춘다. 저장소 설정 변경이므로 사용자에게 `classification.md` "상태 라벨"의 이름·설명으로 만드는 `gh label create` 명령을 보여준다.

## 1단계: 조회

열린 Issue 전체를 GraphQL 한 번으로 읽는다. GitHub MCP에는 blocked by와 하위 Issue를 한 번에 읽는 조회가 없어 `gh`를 쓴다.

```sh
gh api graphql -f owner=<owner> -f repo=<repo> -f query='
query($owner:String!,$repo:String!,$after:String){ repository(owner:$owner,name:$repo){
  issues(states:OPEN, first:100, after:$after){ totalCount pageInfo{hasNextPage endCursor} nodes{
    number title url updatedAt
    labels(first:10){nodes{name}}
    parent{number}
    subIssues(first:50){nodes{number state}}
    blockedBy(first:20){nodes{number state}}
    blocking(first:20){nodes{number state}}
}}}}'
```

`hasNextPage`가 참이면 `-f after=<endCursor>`로 끝까지 넘긴다. 가져온 수와 `totalCount`를 비교한다. 다르거나 호출이 실패하면 "일부 조회(n/N)" 또는 "조회 실패"로 기록하고, 이후 어디에서도 "전체 후보"라고 하지 않는다.

## 2단계: 분류

`references/classification.md`로 Issue마다 상태, 카테고리, 관계 안내를 정한다. 후보는 미선택 Issue뿐이다.

## 3단계: 사용자 선택 (체크박스)

1. 터미널에 조회 범위, 현재 오늘 목록(`SELECTED`·`IN_PROGRESS`), 카테고리별 후보 목록을 먼저 보여준다. 형식은 `formats.md` "오늘작업"과 같다. 넘친 후보(아래 3), 상위 묶음, 상태 라벨 중복은 번호와 제목만 따로 쓴다.
2. "후보만" 요청이면 여기서 끝낸다. 오늘 목록에 넣으려면 "오늘 계획 세워줘"로 다시 요청하라고 한 줄로 안내한다.
3. 후보가 없으면 체크박스를 띄우지 않고 그렇다고 알린 뒤 끝낸다.
4. `AskUserQuestion`을 `multiSelect: true`로 한 번 호출한다. 질문은 카테고리 하나에 하나, 선택지는 `classification.md` "체크박스 구성"을 따른다. 도구 상한은 질문 4개, 질문당 선택지 4개다.
5. 고른 항목과 "Other"에 적은 번호를 합친다. Other의 번호가 1단계 결과에 없거나 미선택이 아니면 무엇이 문제인지 알리고 다시 묻는다.
6. 아무것도 고르지 않았으면 기록하지 않고 끝낸다.
7. 막힌 Issue를 골라도 막지 않는다. 선택은 사용자의 권한이다. 결과에 막힘 안내가 붙는다.
8. 이 단계까지는 라벨을 바꾸지 않고 Discord에 아무것도 보내지 않는다.

## 4단계: 상태 라벨 기록

요청 종류마다 바꿀 Issue를 정한다. 바꿀 것이 없는 Issue는 호출하지 않는다.

| 종류                 | 대상             | 명령                                        | 대상이 아니면                                                                           |
| -------------------- | ---------------- | ------------------------------------------- | --------------------------------------------------------------------------------------- |
| 추가 선택, 직접 지정 | 미선택 Issue     | `gh issue edit <N> --add-label SELECTED`    | 이미 `SELECTED`·`IN_PROGRESS`면 그대로 두고 알린다. 닫힘·없는 번호·상위 묶음이면 알린다 |
| 제외                 | `SELECTED` Issue | `gh issue edit <N> --remove-label SELECTED` | 미선택이면 그대로 두고 알린다. `IN_PROGRESS`면 이 스킬이 다루지 않는다고 알린다         |

- 바꿀 Issue가 하나도 없으면(같은 요청 반복 등) 라벨을 바꾸지 않고, 5단계 알림도 보내지 않는다.
- 호출은 Issue마다 따로라 일부만 성공할 수 있다. 실패해도 되돌리지 않고, 나머지 Issue는 계속 진행한다.
- 호출이 끝나면 1단계 조회를 다시 실행해 **실제로 붙은 상태 라벨**을 오늘 목록으로 삼는다. 의도한 결과와 다른 Issue를 번호로 모아 둔다. 같은 요청을 다시 하면 남은 Issue만 바뀐다.

## 5단계: Discord 알림

4단계에서 라벨이 하나라도 바뀌었을 때만 보낸다.

1. 재조회한 오늘 목록으로 `.claude/skills/discord-message/references/formats.md`의 "공통 규칙"과 "오늘작업" 형식 본문을 만든다. 항목 순서는 `classification.md` "결과 순서"를 따른다.
2. `.claude/skills/discord-message/references/tools.md`(이하 `tools.md`)의 "도구 준비", "대상 채널", "전송"을 따라 새 메시지로 보낸다. 이전 알림을 찾거나 고치지 않는다.
3. 성공 여부는 도구의 성공 응답으로만 판정한다. 실패·부분 전송·응답 없음은 `tools.md` "실패 처리"를 따르고 무조건 재시도하지 않는다. 알림이 실패해도 라벨 기록은 그대로 둔다.

## 6단계: 결과 안내

- **기록**: 대화창에 재조회한 오늘 목록을 Discord 본문과 같은 형식으로 보여주고, 붙이거나 뗀 Issue 번호를 알린다. 바뀐 것이 없으면 "변경 없음"이라고 쓴다.
- **어긋남**: 4단계에서 의도와 다른 Issue가 있으면 `#24 라벨 붙이기 실패: <오류 문구>`처럼 한 줄씩 알리고, 같은 요청을 다시 하면 남은 것만 바뀐다고 안내한다. 기록 완료라고 쓰지 않는다.
- **알림**: 보냈으면 채널 ID와 메시지 ID를, 보내지 않았으면 이유(변경 없음, 연결 안 됨, 실패)를 쓴다. 메시지 ID를 지어내지 않는다.
- **선행 누락**: 고른 막힌 Issue의 실제 선행(`classification.md` "실제 선행")이 오늘 목록에 없으면 `#27의 선행 #29가 오늘 목록에 없음`처럼 한 줄씩 알린다. 선택을 바꾸라고 하지 않는다.
- 코딩은 새 세션에서 Issue 링크로 따로 시작하라고 한 줄 덧붙인다. 코딩을 시작하지 않는다.

여기서 계획 세션은 끝난다.

## 오류 처리

| 상황                       | 할 일                                                             |
| -------------------------- | ----------------------------------------------------------------- |
| GitHub 인증 만료·권한 거부 | 재시도하지 않는다. 오류 문구를 알리고 멈춘다                      |
| 상태 라벨이 저장소에 없음  | 만들지 않는다. 0단계 4의 `gh label create` 명령을 보여주고 멈춘다 |
| 라벨 호출 일부 실패        | 되돌리지 않는다. 재조회 결과와 실패한 Issue를 알린다              |

## 테스트 시나리오

### 정상 흐름

1. **추가 선택**: "오늘 계획 세워줘" → 조회 → 분류 → 터미널에 현재 오늘 목록과 후보 → 체크박스(미선택 Issue만) → 고름 → `SELECTED` 추가 → 재조회 → 새 Discord 알림 → 대화창에 같은 목록과 메시지 ID.
2. **제외**: "#24 빼줘" → 조회 → #24가 `SELECTED` → 라벨 제거 → 재조회 → 알림.
3. **같은 요청 반복**: 이미 `SELECTED`인 #23을 다시 올려 달라고 함 → 바꿀 것 없음 → 라벨 호출·알림 없음, "변경 없음".
4. **후보만**: "열린 이슈 구분해서 보여줘" → 터미널 목록 후 종료. 체크박스·라벨·Discord 호출 없음.
5. **진행 중 Issue**: #22가 `IN_PROGRESS` → 체크박스에 없음, 오늘 목록에 `🔄 진행 중`. "#22 빼줘" → 다루지 않는다고 알림.
6. **카테고리 넘침**: feature 미선택 후보가 6건 → 체크박스에 4건, 나머지 2건은 터미널에 번호만 → Other에 번호 입력으로 선택 가능.
7. **후보 1개 카테고리**: refactor 후보가 #26 하나 → 선택지 `#26`과 `고르지 않음` → `고르지 않음`은 기록하지 않음.
8. **막힌 Issue 선택**: #24(blocked by #22)를 고름 → 막지 않음 → 결과에 `← #22`, #22가 오늘 목록에 없으면 선행 누락 안내.
9. **상위 묶음**: #21(열린 하위 있음) → 체크박스·오늘 목록에 없음, 터미널에 번호와 제목만.
10. **상위 묶음이 선행**: #27(blocked by #19), #19의 열린 하위는 #29 → #27 아래에 `← #19`, 그 다음 줄에 두 칸 더 들여 `└─ #29 남음`. 체크박스의 #29 설명에는 `🔓 끝내면 #27 시작 가능 (#19 닫은 뒤)`를 쓰되 Discord 메시지에는 반복하지 않는다. 둘 다 고르면 #29가 먼저.
11. **분류 경계**: blocked by가 열려 있으면 막힘, 본문에만 적힌 의존은 막힘이 아님. 진행 중은 `IN_PROGRESS` 라벨로만 판정하고 PR·담당자로 추론하지 않음.

### 오류 흐름

1. **라벨 일부 실패**: #23은 붙고 #24는 권한 오류 → 되돌리지 않음 → 재조회 목록에 #23만 → `#24 라벨 붙이기 실패` 안내 → 알림은 실제 목록으로 보냄.
2. **알림 실패**: 응답이 `reply failed: channel not allowlisted` → 재시도하지 않음 → 오류 문구와 `/discord:access` 안내 → 라벨 기록은 유지, 대화창에 목록과 "알림 미전송".
3. **라벨 없음**: 저장소에 `SELECTED`가 없음 → 만들지 않고 `gh label create` 명령 안내 후 멈춤.
4. **GitHub 인증 만료**: GraphQL 조회가 권한 오류 → 재시도하지 않고 오류 문구를 알린 뒤 멈춤. 라벨·Discord 호출 없음.
5. **상태 라벨 중복**: 한 Issue에 `SELECTED`와 `IN_PROGRESS`가 함께 있음 → 후보·오늘 목록에서 빼고 터미널에 `⚠️ 상태 라벨 중복`으로 알림. 이 스킬이 고치지 않음.
6. **아무것도 고르지 않음**: 체크박스에서 선택 없음 → 기록하지 않고 종료. 4~6단계 작업은 `completed`로 바꾸지 않음.
