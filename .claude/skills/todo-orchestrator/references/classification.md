# Issue 판정 기준

1단계 조회 결과로 Issue마다 상태·카테고리·관계를 정한다. 판정 기준은 이 파일에만 둔다.

출력 배치는 정하지 않는다. Discord 본문은 `formats.md`, 터미널 목록과 체크박스는 `SKILL.md` 3단계가 정한다.

## 상태 라벨

오늘 목록의 원본이다. 문자열 유니언 `'SELECTED' | 'IN_PROGRESS'`이고, 라벨 이름이 곧 값이다.

| 라벨          | 뜻                                             |
| ------------- | ---------------------------------------------- |
| `SELECTED`    | 오늘 할 작업으로 선택했고 아직 시작하지 않음   |
| `IN_PROGRESS` | 작업을 시작함. 리뷰 중·판단 대기도 여기에 든다 |

- 오늘 목록은 상태 라벨이 붙은 열린 Issue 전체다. 날짜가 바뀌어도 라벨을 정리하지 않는다.
- Discord 메시지는 알림이다. 다시 읽어 판단에 쓰지 않는다. 날짜별 Issue·Markdown 일지·DB도 만들지 않는다.
- 완료는 Issue 닫힘, 선행 대기는 Relationships의 blocked by, 하지 않기로 한 Issue는 닫힘 사유로 이미 알 수 있어 라벨로 두지 않는다.
- Issue마다 상태 라벨은 최대 하나다. GitHub가 강제하지 않으므로 조회 결과로 확인한다.

## 상태

Issue마다 위에서부터 처음 맞는 하나로 정한다.

| 상태      | 판정                        | 후보 | 오늘 목록 | 표시                |
| --------- | --------------------------- | ---- | --------- | ------------------- |
| 상위 묶음 | `subIssues`에 `OPEN`이 있다 | ✗    | ✗         | 번호와 제목만       |
| 라벨 중복 | 상태 라벨이 둘 이상이다     | ✗    | ✗         | `⚠️ 상태 라벨 중복` |
| 진행 중   | `IN_PROGRESS` 라벨이 있다   | ✗    | ✓         | `🔄 진행 중`        |
| 선택됨    | `SELECTED` 라벨이 있다      | ✗    | ✓         | 표시 없음           |
| 미선택    | 위에 해당하지 않는다        | ✓    | ✗         | 표시 없음           |

- 상위 묶음을 후보에서 빼는 이유는 열린 하위 Issue로 세어 같은 작업을 두 번 세지 않기 위해서다. 선택 단위는 독립적으로 시작하고 검증할 수 있는 Issue 하나다.
- 라벨 중복은 고치지 않는다. 판정만 하고 사용자에게 알린다.
- 막힘은 상태와 별개다. `blockedBy`에 `OPEN`이 있으면 후보와 오늘 목록 모두에 `← #N`을 붙인다.
- 진행 중은 `IN_PROGRESS` 라벨로만 판정한다. 연결 PR이나 담당자로 추론하지 않는다.
- 선행은 Relationships의 blocked by만이다. 본문 문장이나 코드 의존으로 추론하지 않는다(`docs/git/issue.md`의 "관계").
- 조회 결과에 없는 상태를 지어내지 않는다.

## 실제 선행

상위 묶음은 후보에 없어 고를 수 없다. 선행이 상위 묶음을 가리키면 고를 수 있는 작업으로 이어지지 않으므로, 결과 순서와 선행 누락 안내는 "실제 선행"으로 계산한다.

- Issue의 `blockedBy` 중 `OPEN`인 것을 하나씩 본다.
- 상위 묶음이 아니면 그대로 실제 선행이다.
- 상위 묶음이면 그 대신 열린 하위 Issue들이 실제 선행이고, 각각 그 상위 번호를 기억한다. 하위 Issue는 1단계 결과에서 그 상위 번호의 `subIssues`로 찾는다. 하위도 상위 묶음이면 같은 방식으로 한 번 더 펼친다.
- 상위 Issue는 하위가 모두 닫혀도 저절로 닫힌다고 가정하지 않는다.
- 실제 선행 자체의 선행은 펼치지 않는다. 한 단만 본다.

## 카테고리

라벨로 카테고리를 정한다. 라벨 기준은 `docs/git/issue.md`의 "템플릿과 라벨"이다.

| 순서 | 카테고리   | 라벨            |
| ---- | ---------- | --------------- |
| 1    | `bug`      | `bug`           |
| 2    | `feature`  | `feature`       |
| 3    | `refactor` | `refactor`      |
| 4    | `other`    | `docs`, `chore` |

- 종류 라벨은 위 표의 다섯 개뿐이다. 상태 라벨과 GitHub 기본 라벨은 세지 않는다.
- 종류 라벨이 없거나 둘 이상이면 `other`에 넣고 `(라벨 확인 필요)`를 붙인다.

## 결과 순서

1. 카테고리 순서
2. 카테고리 안에서, 오늘 목록의 다른 Issue의 실제 선행인 Issue를 먼저 둔다
3. 그 외에는 진행 중 → 선택됨(막히지 않음) → 선택됨(막힘), 같으면 번호순

## 표시 어휘

판정 결과를 가리키는 문자열이다. 어디에 어떻게 놓을지는 소비자가 정한다.

| 어휘                                  | 조건                                                                        |
| ------------------------------------- | --------------------------------------------------------------------------- |
| `🔄 진행 중`                          | 상태가 진행 중                                                              |
| `⚠️ 상태 라벨 중복`                   | 상태가 라벨 중복                                                            |
| `(라벨 확인 필요)`                    | 종류 라벨이 없거나 둘 이상                                                  |
| `← #N`                                | 직접 선행. 여럿이면 `← #N, #M`으로 모두 쓴다                                |
| `└─ #N, #M 남음`                      | 바로 위 직접 선행이 상위 묶음이고, #N·#M이 그 묶음의 실제 선행이다          |
| `🔓 끝내면 #N 시작 가능`              | 이 Issue가 #N의 실제 선행이고, 이 Issue를 빼면 #N의 실제 선행이 남지 않는다 |
| `🔓 끝내면 #N 시작 가능 (#P 닫은 뒤)` | 위와 같고, 이 Issue가 상위 묶음 #P를 펼쳐 나온 실제 선행이다                |
| `⬆ 상위 #N`                           | `parent`가 있다                                                             |

- `←`는 오른쪽 Issue가 완료되어야 선행 조건이 해소된다는 뜻이다. 상태 표시와 별개다.
- `└─`의 작업들이 완료되어도 상위 묶음 자체가 닫혀야 선행 조건이 해소된다.
- 번호는 오름차순이다.
- Relationships로 확인한 관계만 쓴다. 목록 순서로 작업 순서를 추정하지 않는다.
