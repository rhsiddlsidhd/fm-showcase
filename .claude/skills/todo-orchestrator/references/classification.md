# 후보 분류 기준

메인 세션이 1단계 GraphQL 조회 결과로 분류한다. 판정이 어긋나지 않도록 기준은 이 파일에만 둔다. 고칠 때는 이 파일만 고친다.

## 선택 단위

- 독립적으로 시작하고 검증할 수 있는 Issue 하나가 단위다.
- 열린 하위 Issue가 있는 상위 Issue는 후보로 세지 않는다. 하위 Issue로 센다. 같은 작업을 두 번 세지 않기 위해서다.

## 상태 라벨

오늘 목록의 원본이다. 문자열 유니언 `'SELECTED' | 'IN_PROGRESS'`이고, 라벨 이름이 곧 값이다.

| 라벨          | 뜻                                             | 설명 문구(GitHub)                                  |
| ------------- | ---------------------------------------------- | -------------------------------------------------- |
| (없음)        | 미선택                                         | -                                                  |
| `SELECTED`    | 오늘 할 작업으로 선택했고 아직 시작하지 않음   | 오늘 할 작업으로 선택했고 아직 시작하지 않은 Issue |
| `IN_PROGRESS` | 작업을 시작함. 리뷰 중·판단 대기도 여기에 든다 | 작업을 시작한 Issue (리뷰·판단 대기 포함)          |

- 완료는 Issue 닫힘이다. 라벨로 두지 않는다.
- 선행 대기는 Relationships의 blocked by, 하지 않기로 한 Issue는 닫힘 사유로 이미 알 수 있어 라벨로 두지 않는다.
- Issue마다 상태 라벨은 최대 하나다. GitHub가 강제하지 않으므로 조회 결과로 확인한다.

## 상태

Issue마다 위에서부터 처음 맞는 하나로 정한다.

| 상태      | 판정                        | 후보 | 오늘 목록 | 표시                                        |
| --------- | --------------------------- | ---- | --------- | ------------------------------------------- |
| 상위 묶음 | `subIssues`에 `OPEN`이 있다 | ✗    | ✗         | 터미널에 번호와 제목만                      |
| 라벨 중복 | 상태 라벨이 둘 이상이다     | ✗    | ✗         | 터미널에 `⚠️ 상태 라벨 중복`. 고치지 않는다 |
| 진행 중   | `IN_PROGRESS` 라벨이 있다   | ✗    | ✓         | `🔄 진행 중`                                |
| 선택됨    | `SELECTED` 라벨이 있다      | ✗    | ✓         | 표시 없음                                   |
| 미선택    | 위에 해당하지 않는다        | ✓    | ✗         | 표시 없음                                   |

- 막힘은 상태와 별개다. `blockedBy`에 `OPEN`이 있으면 후보와 오늘 목록 모두에서 아래 관계 표기법으로 `← #N`을 붙인다.
- 진행 중은 `IN_PROGRESS` 라벨로만 판정한다. 연결 PR이나 담당자로 추론하지 않는다.
- 선행은 Relationships의 blocked by만이다. 본문 문장이나 코드 의존으로 추론하지 않는다(`docs/git/issue.md`의 "관계").
- 조회 결과에 없는 상태를 지어내지 않는다.

## 실제 선행

상위 묶음은 후보에 없어 고를 수 없다. 선행이 상위 묶음을 가리키면 고를 수 있는 작업으로 이어지지 않으므로, 결과 순서와 선행 누락 안내는 "실제 선행"으로 계산한다. 관계 표시는 원래 선행인 상위 번호를 유지하고, 실제 선행은 선택지 설명에서 괄호로, 메시지에서 다음 줄의 `└─`로 표시한다.

- Issue의 `blockedBy` 중 `OPEN`인 것을 하나씩 본다.
- 상위 묶음이 아니면 그대로 실제 선행이다.
- 상위 묶음이면 그 대신 열린 하위 Issue들이 실제 선행이고, 각각 그 상위 번호를 기억한다. 하위 Issue는 1단계 결과에서 그 상위 번호의 `subIssues`로 찾는다. 하위도 상위 묶음이면 같은 방식으로 한 번 더 펼친다.
- 상위 Issue는 하위가 모두 닫혀도 저절로 닫힌다고 가정하지 않는다.

## 관계 안내

선택지 설명은 아래 표의 해당 항목만 `·`로 이어 한 줄로 쓴다. 터미널 목록과 Discord 오늘작업 메시지에는 아래 "메시지 관계 표기법"을 적용한다.

| 안내                                  | 조건                                                                        |
| ------------------------------------- | --------------------------------------------------------------------------- |
| `← #N`                                | 직접 선행. 여럿이면 `← #N, #M`으로 모두 쓴다                                |
| `← #P (#N, #M 남음)`                  | 직접 선행이 상위 묶음 #P이고, #N·#M이 그 묶음의 실제 선행이다               |
| `🔓 끝내면 #N 시작 가능`              | 이 Issue가 #N의 실제 선행이고, 이 Issue를 빼면 #N의 실제 선행이 남지 않는다 |
| `🔓 끝내면 #N 시작 가능 (#P 닫은 뒤)` | 위와 같고, 이 Issue가 상위 묶음 #P를 펼쳐 나온 실제 선행이다                |
| `⬆ 상위 #N`                           | `parent`가 있다                                                             |

### 메시지 관계 표기법

- `←`는 오른쪽 이슈가 완료되어야 해당 작업의 선행 조건이 해소된다는 뜻이다. 상태나 담당자 표시는 별개다.
- 각 작업 바로 아래에 두 칸 들여 쓴다. 일반 선행은 한 줄, 상위 묶음은 두 줄이다. 열린 직접 선행이 없으면 관계 줄을 생략한다.
- 단일 선행은 `← #29`, 여러 선행은 `← #29, #30`으로 쓴다. 번호는 오름차순이다.
- 직접 선행이 상위 묶음이면 첫 줄은 `← #19`, 다음 줄은 두 칸 더 들여 `└─ #29, #30 남음`으로 쓴다. `└─`는 바로 위 묶음의 열린 실제 선행이며, 이들이 완료되어도 #19 자체가 닫혀야 선행 조건이 해소된다.
- 상위 묶음이 여러 개면 묶음마다 두 줄을 반복한다. 일반 선행은 한 줄로 묶어 별도로 표시하고, 각 줄 또는 묶음의 첫 번호순으로 정렬한다. 남은 작업 번호도 오름차순이다.
- 선행 작업 자체의 의존 관계는 여기서 재귀적으로 펼치지 않는다. #30이 #29를 기다리면 #30 항목 아래에 `← #29`를 쓴다. 묶음의 남은 작업은 `└─` 한 줄에 나열하고, 그 아래로 트리나 관계용 코드블록을 추가하지 않는다.
- 메시지에는 선행 방향만 표시한다. 역방향의 `🔓 끝내면…`과 해당 작업 자신의 `⬆ 상위…`는 반복하지 않는다. 관계 번호는 일반 텍스트로 쓰고, 작업 항목의 번호에만 링크를 건다.
- Relationships로 확인한 관계만 표시하고, 목록 순서만으로 작업 순서를 추정하지 않는다.

## 카테고리

라벨로 카테고리를 정한다. 라벨 기준은 `docs/git/issue.md`의 "템플릿과 라벨"이다.

| 순서 | 카테고리   | 라벨            |
| ---- | ---------- | --------------- |
| 1    | `bug`      | `bug`           |
| 2    | `feature`  | `feature`       |
| 3    | `refactor` | `refactor`      |
| 4    | `other`    | `docs`, `chore` |

- 종류 라벨이 없거나 둘 이상이면 `other`에 넣고 항목 끝에 `(라벨 확인 필요)`를 붙인다.
- 종류 라벨은 위 표의 다섯 개뿐이다. 상태 라벨과 GitHub 기본 라벨은 세지 않는다.
- 카테고리가 4개라 체크박스 질문 상한(4개)과 맞는다.

## 체크박스 구성

- 후보가 있는 카테고리만 질문으로 만들고, 위 카테고리 순서로 둔다. `header`는 카테고리 이름이다.
- 질문당 선택지는 최대 4개다. 카테고리 안의 미선택 Issue에서 막히지 않은 것 → 막힌 것 순, 같으면 최근 갱신순으로 4개를 고른다.
- 후보가 1개인 카테고리는 선택지 `고르지 않음`(description `이 카테고리에서는 고르지 않음`)을 뒤에 더한다. 도구가 질문마다 선택지를 2개 이상 요구하기 때문이다. `고르지 않음`은 기록하지 않고, 같은 질문에서 다른 항목과 함께 골라도 무시한다.
- 4개를 넘친 후보는 터미널 목록에 번호와 제목만 쓰고, "Other"에 번호를 적어 고를 수 있다고 질문 문장에 쓴다.
- 선택지 `label`은 `#번호 제목`이고, 제목이 길면 줄인다. `description`은 관계 안내다. 없으면 `시작 가능`이라고 쓴다.

## 결과 순서

1. 카테고리 순서
2. 카테고리 안에서, 오늘 목록의 다른 Issue의 실제 선행인 Issue를 먼저 둔다
3. 그 외에는 진행 중 → 선택됨(막히지 않음) → 선택됨(막힘), 같으면 번호순
