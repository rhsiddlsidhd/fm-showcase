# spec.md 형식

`_workspace/00_input/spec.md`의 형식이다. 오케스트레이터만 쓴다. 섹션 제목과 배치 표의 첫 두 칸(경로, 역할)은 `guard.sh`가 읽으므로 바꾸지 않는다.

```markdown
# {기능 이름}

## 요구사항

| ID  | 요구사항                   | 출처                             |
| --- | -------------------------- | -------------------------------- |
| R1  | {관찰 가능한 동작 한 가지} | {사용자 요청 / 챌린지 자료 경로} |

## 파일 배치

| 경로                 | 역할 | 레이어/세그먼트 | 요구사항 | 이유                           |
| -------------------- | ---- | --------------- | -------- | ------------------------------ |
| `{src/...}`          | impl | {layer/segment} | R1       | {docs/architecture/ 문서#앵커} |
| `{src/....test.tsx}` | test | {layer/segment} | R1       | {docs/testing/ 문서#앵커}      |

## 인터페이스 계약

| 경로        | 내보내는 이름 | 형태                                |
| ----------- | ------------- | ----------------------------------- |
| `{src/...}` | `{Name}`      | `{(props: { ... }) => JSX.Element}` |

## 배치 변경 기록

| 호출 | 바꾼 경로 | 이유 |
| ---- | --------- | ---- |
```

## 칸 규칙

- `ID`: `R` + 숫자. 한 번 붙인 번호는 바꾸거나 다시 쓰지 않는다. 테스트 이름과 보고서가 이 번호로 대응을 확인한다.
- `역할`: `impl` 또는 `test`만 쓴다. `test`는 테스트 파일 패턴, `impl`은 테스트 파일을 뺀 `src/**`여야 한다(`G plan`이 검사).
- `요구사항`: 쉼표로 구분한 ID. public API(`index.ts`)처럼 요구사항에 직접 대응하지 않으면 `—`.
- `이유`: 배치 근거가 되는 문서의 `경로#앵커`만 쓴다. 설명이나 예외 사유를 쓰지 않는다. 근거를 문서에서 찾지 못하면 배치를 확정하지 말고 사용자에게 묻는다.
  - 이유: 문서 규약의 예외는 사용자만 정한다. 오케스트레이터가 이 칸에 예외 사유를 쓰면 규약을 스스로 면제하는 셈이 되고, verifier가 그 설명을 근거로 따라가게 된다.
- `인터페이스 계약`: 테스트와 구현이 서로 맞춰야 하는 것만 쓴다. 내보내는 이름, props·인자·반환 형태다. 구현 방식(어디서 값을 가공하는지 등), 표현·컨테이너 분류, 무엇을 테스트할지는 쓰지 않는다.
  - 이유: 구현 방식은 executor가, 테스트 범위는 test-engineer가 판단한다. 오케스트레이터가 계약에 적으면 그 판단을 미리 정해 버린다. 첫 실행에서 "표현 컴포넌트"라는 문구가 test-engineer의 테스트 범위를 정했다.
- `배치 변경 기록`: 1단계 뒤에 배치 표를 고칠 때마다 한 행을 추가한다. 처음 배치는 적지 않는다.
