# test-engineer 입출력

- 역할: 요구사항마다 실패하는 테스트를 쓴다
- 문서 인덱스: `docs/testing/README.md`
- 판정 값: `RED`

## 입력 파일 내용

| 섹션           | 채우는 내용                                                    | 가져오는 곳                                          |
| -------------- | -------------------------------------------------------------- | ---------------------------------------------------- |
| 요구사항       | 모든 요구사항의 ID와 문구                                      | spec.md `## 요구사항`의 첫 두 칸                     |
| 수정 가능 경로 | `test` 행 경로                                                 | spec.md `## 파일 배치`                               |
| 참조 파일      | `impl` 행 경로. 용도는 "import할 구현 경로(아직 없을 수 있음)" | spec.md `## 파일 배치`                               |
| 테스트 대응    | `없음`                                                         | —                                                    |
| 재호출 사유    | `MISSING`·`WRONG` 행, 또는 `테스트 문제` 행, 또는 위반 경로    | 직전 verifier·executor 보고서, `{NN}_violations.txt` |

배치 표의 `이유` 칸은 옮기지 않는다.

## 작업 지시

- `수정 가능 경로`마다 테스트를 쓴다. 테스트 이름에 요구사항 ID를 넣는다(예: `R1: ...`).
- `npm test`를 실행해 실패를 확인한다. 구현 파일이 없어 import가 실패하는 것은 정상적인 실패다. 테스트 코드 자체의 문법·타입 오류는 실패로 인정하지 않는다.
- `checks.sh test-engineer`는 통과해야 한다. 구현이 없어 실패할 수밖에 없는 명령은 스크립트가 뺀다.
- 재호출이면 `재호출 사유`에 적힌 것만 고친다.

## 에이전트별 출력 섹션

```markdown
## 테스트 대응

| 요구사항 | 테스트 파일 | 테스트 이름  | 실패 이유                       |
| -------- | ----------- | ------------ | ------------------------------- |
| R1       | `{path}`    | `R1: {name}` | {구현 없음 / 기대값 불일치 ...} |
```

- 요구사항마다 한 행 이상 있어야 한다. 테스트하지 않는 요구사항은 `테스트 파일`에 `—`를 쓰고, `실패 이유` 칸에 그 근거 문서를 적는다. 이 칸은 verifier만 읽는다.
