# 구현 오케스트레이터

## 실행 모드: 서브에이전트 위임

에이전트를 한 명씩 차례로 부른다. 앞 단계의 결과가 다음 단계의 입력이라 병렬 호출은 없다. `collaboration.spawn_agent`로 호출마다 새 에이전트를 만들고 `fork_turns="none"`을 지정한다. `task_name`은 역할과 호출 순번으로 정한다. 전체 대화를 상속시키지 않고 역할별 프롬프트만 전달한다. 완료 결과를 받기 전에는 다음 단계로 가지 않는다. 사용할 수 없는 도구 이름은 현재 세션의 동등한 위임 도구에 맞춰 바꾸되 새 대화·순차 실행·읽기 범위 원칙을 유지한다. 에이전트끼리 통신하지 않는다.

**이 순서를 지키는 이유:** 이 저장소는 "테스트를 구현보다 먼저 썼다"를 커밋 순서로 증명한다(`docs/testing/test-policy.md`의 테스트 선행). 그래서 executor는 RED 확인과 테스트 커밋이 끝난 뒤에만 부른다. 이 순서는 모델이 아니라 아래 절차의 확인 단계가 지킨다.

## 에이전트 구성

OMC 5.7.5 전문 에이전트의 원본 본문을 보존한 `.codex/agents/omc-*.toml`을 사용한다. 각 파일의 `developer_instructions` 뒤에 이 하네스의 역할별 프롬프트를 붙인다. TOML의 Codex 이식·저장소 우선 규칙이 OMC 원본보다 우선하고, 호출별 범위·검증·보고서 지시가 그보다 구체적이다.

| 역할        | 원본 OMC 전문 에이전트             | 원본 모델                         | Codex 정의                               | Codex 모델·추론                                                        |
| ----------- | ---------------------------------- | --------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------- |
| 테스트 작성 | `oh-my-claudecode:test-engineer`   | `opus`                            | `.codex/agents/omc-test-engineer.toml`   | `gpt-6.1-sol`, `high`                                                  |
| 구현        | `oh-my-claudecode:executor`        | `sonnet`, 구현 문제 재시도 `opus` | `.codex/agents/omc-executor.toml`        | 첫 호출 `gpt-6-luna`, `medium`; 구현 문제 재시도 `gpt-6.1-sol`, `high` |
| 정리        | `oh-my-claudecode:code-simplifier` | `opus`                            | `.codex/agents/omc-code-simplifier.toml` | `gpt-6.1-sol`, `high`                                                  |
| 종합 검증   | `oh-my-claudecode:verifier`        | `opus`                            | `.codex/agents/omc-verifier.toml`        | `gpt-6.1-sol`, `high`                                                  |

모델 배정은 원본 실행 오케스트레이터의 역할별 배정이 기준이다(원본 개별 에이전트의 기본 모델과 다를 수 있다). 사용자 지시(2026-11-09)로 전체 서브에이전트 모델을 한 단계 낮췄다. Opus 역할→Sol, Sonnet 역할→Luna는 역할·비용 구분을 보존하기 위한 선정이며 모델 성능 동등성을 뜻하지 않는다. Claude/OMC 런타임을 실행하는 것이 아니라 원본 전문 지침을 Codex 런타임에서 실행한다.

호출 전에 해당 TOML을 읽어 `name`, `model`, `model_reasoning_effort`, `developer_instructions`를 확인한다. 현재 위임 도구가 커스텀 에이전트 선택을 지원하면 그 정의를 사용한다. `collaboration.spawn_agent`처럼 `agent_type` 선택 인자가 없으면 `fork_turns="none"`과 명시적 `model`·`reasoning_effort`를 지정하고, `developer_instructions` 전문 + 공통 블록 + 역할별 블록을 `message`로 전달한다. 전체 프롬프트가 메시지 길이에 비해 크면 그 전문을 기록한 파일을 첫 작업으로 전부 읽도록 전달할 수 있다. 이때 전문 로드 사실을 보고받고, 역할 이름만으로 작업하거나 다른 기록을 읽게 하지 않는다. 원본 지침 없이 역할 이름만 붙이는 호출은 하지 않는다. 실제 전달한 전문을 `_workspace/{NN}_{agent}_prompt.md`에 저장한다.

도구와 권한은 부모 세션을 상속한다. verifier의 원본 `disallowedTools: Write, Edit`는 파일 쓰기 금지 지시로 대응하며 도구 수준 차단은 아니다. 역할별 읽기·쓰기 범위도 프롬프트 지시다. OMC의 `level` 메타데이터는 Codex 필드로 만들지 않는다. 원본 라이선스는 `.codex/agents/OMC-LICENSE`에 보존한다.

**경로 구분:** 테스트 경로는 `*.test.*`, `*.spec.*`, `e2e/**`, `src/shared/test/**`다. 구현 경로는 테스트 경로를 뺀 `src/**`다. 설정 파일, `docs/`, `AGENTS.md`, `package.json`, `.sdd/`는 어느 에이전트도 고치지 않는다. 바꿔야 하면 멈추고 사용자에게 묻는다.

**경로를 나누는 이유:** executor가 테스트를 고칠 수 있으면 구현 대신 테스트를 바꿔 통과시키는 쉬운 길을 고를 수 있다. code-simplifier도 같다. 테스트를 "단순화"하는 것도 명세를 바꾸는 일이다.

**읽기 범위:** 에이전트는 자기 역할의 근거만 읽는다(`AGENTS.md` 우선순위의 예외). 오케스트레이터는 프롬프트에 범위 밖 파일의 경로나 내용을 옮겨 적지 않는다. 막는 방식은 프롬프트 지시뿐이다.

| 역할        | 읽는 것                                                                                                | 읽지 않는 것                                 | 이유                                                                                      |
| ----------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 테스트 작성 | `.sdd/<슬라이스>/`, `docs/testing/`, 기존 테스트 파일, 기존 `src/`의 타입·export 시그니처(import 대상) | 구현 함수 본문, `docs/testing/` 밖의 `docs/` | 기대값은 구현 밖에서 와야 한다. 구현을 보면 결과를 베낄 수 있다                           |
| 구현        | 테스트 파일, 기존 `src/`                                                                               | `.sdd/`, `docs/`                             | 테스트가 명세의 전부여야 테스트 커밋 → 구현 커밋 순서가 "테스트로 구현했다"의 증거가 된다 |
| 정리        | 기존 `src/`, 테스트 파일(동작 기준), `docs/architecture/`                                              | `.sdd/`, `docs/architecture/` 밖의 `docs/`   | 정리는 구조를 다듬는 일이라 구조 규칙이 근거다. 요구사항은 테스트가 대신한다              |
| 종합 검증   | 전부                                                                                                   | 없음                                         | 요구사항·테스트·구현·커밋을 대조하는 판정 역할이다                                        |

## 작업 기록 (`_workspace/`)

`_workspace/`는 `.gitignore` 대상이다. 오케스트레이터만 쓴다. 에이전트는 보고서를 최종 응답으로 돌려주고, 오케스트레이터가 그 전문을 저장한다.

```
_workspace/
├── 00_plan.md                 요구사항 출처와 바퀴 표 (1단계)
├── run_log.md                 호출·확인·커밋마다 한 줄
├── mapping.md                 요구사항 ↔ 테스트 대응표 (바퀴마다 누적)
├── {NN}_{agent}_prompt.md     에이전트에 보낸 프롬프트 전문
├── {NN}_{agent}_report.md     에이전트 보고서 전문
└── {NN}_checks.md             오케스트레이터가 직접 실행한 명령과 결과
```

- `NN`은 호출 순번 01, 02, …다. 재호출도 새 번호를 받는다.
- `run_log.md` 한 줄 형식: `| NN | 바퀴 | 단계 | 결과 | 재시도 사용 수 | 근거 파일 |`
- 직접 확인한 사실(명령 출력, 파일 내용)만 기록한다. 에이전트의 판단을 추측해 채우면 사후 검증 기록을 위조하는 셈이다.

## 작업 절차

### 0단계: 시작 확인

1. `git branch --show-current`가 `main`이거나 비어 있으면(분리된 HEAD) 멈추고 브랜치를 묻는다. 이 스킬은 커밋을 만들고, `main`에는 훅이 커밋을 막는다.
2. `_workspace/` 상태로 분기한다.
   - **없음:** `git status --porcelain -uall`이 비어 있어야 한다. 비어 있지 않으면 멈추고 묻는다. 매 단계 "에이전트가 바꾼 파일 = `git status`에 보이는 파일"이 성립해야 경로 확인이 맞기 때문이다. 이어서 아래 「구현 확인 명령」을 실행해 모두 통과해야 한다. 시작부터 실패하면 에이전트가 자기와 상관없는 실패를 떠안는다. 실패하면 멈추고 실패한 명령을 보여 준다. 통과하면 `git rev-parse HEAD`를 **시작 커밋**으로 `run_log.md` 첫 줄에 남긴다. 구조 작업은 첫 바퀴보다 앞설 수 있으므로, 이번 실행의 커밋 범위는 첫 테스트 커밋이 아니라 시작 커밋에서 센다.
   - **있고 같은 기능의 후속 요청:** `run_log.md`의 마지막 줄과 `git log`를 대조해 어디서 멈췄는지 확인하고, 트리가 깨끗한지 본다. 기록 뒤에 바뀐 파일이 있으면 그 경로를 보여 주고 어떻게 할지 묻는다. 없으면 요청한 단계부터 이어서 한다.
   - **있고 새 기능 요청:** 기존 디렉터리를 `_workspace_{YYYYMMDD-HHMMSS}/`로 옮기고 "없음"과 같이 처리한다.

### 1단계: 계획 (사용자와 대화)

에이전트는 사용자에게 물을 수 없다. 모호한 것은 모두 이 단계에서 묻는다.

1. `.sdd/<슬라이스>/`의 요구사항서, 기능 설계서, 검증 문서를 읽는다. `docs/testing/README.md`와 `docs/architecture/README.md`를 읽고, 그 인덱스가 가리키는 문서 중 배치·층 판단에 필요한 것을 읽는다. 기존 `src/` 구조도 확인한다.
2. 검증 문서에서 테스트로 확인하는 시나리오를 모두 모은다. "사람 확인"으로 적힌 시나리오는 이 스킬의 범위 밖이다. 그 목록은 최종 보고에 남긴다.
   Issue 완료 조건 중 테스트로 확인하지 않는 것(동작이 바뀌지 않는 구조·정의 조건. 예: 라우트 정의 위치, 타입·값 목록 정의)은 바퀴가 아니라 **구조 작업**으로 분류한다. 바퀴의 executor는 테스트만 보므로 이런 조건을 알 수 없기 때문이다. 구조 작업마다 완료 조건 문장, 구현 경로, 판정 명령(`typecheck`·`lint:fsd` 등), 실행 시점(어느 바퀴 앞·뒤)을 정한다.
3. 시나리오를 **바퀴**로 나눈다. 바퀴 하나는 테스트 커밋 하나와 구현 커밋 하나다. 아래 다섯 기준을 모두 만족하게 나눈다.

   | 기준                                                        | 이유                                                             |
   | ----------------------------------------------------------- | ---------------------------------------------------------------- |
   | 구현 대상이 하나다(같은 함수, 또는 같은 동작 컴포넌트 흐름) | executor의 변경이 한 덩어리여야 확인과 되돌리기가 쉽다           |
   | 테스트 층이 하나다                                          | 서로 다른 검증 목적을 한 바퀴에 섞지 않는다                      |
   | 실행 환경이 하나다                                          | 준비 코드와 실행 비용이 달라 섞으면 작업이 흩어진다              |
   | 바퀴 안의 테스트가 모두 구현 전에 실패할 수 있다            | 앞 바퀴의 구현만으로 이미 통과하는 테스트는 RED를 확인할 수 없다 |
   | 앞 바퀴가 만든 것만으로 테스트를 쓸 수 있다                 | 예: 필터 조작이 필요한 알림 갱신은 필터 조작 바퀴 뒤에 둔다      |

   층과 실행 환경은 `docs/testing/test-boundaries.md`에 따라 따로 정한다. 현재 실행 절차는 Vitest(jsdom)의 Unit·Integration과 Playwright E2E를 지원한다. 실제 브라우저에서 실행할 Unit·Integration이 필요하면 실행 절차를 보완하기 전에는 해당 바퀴를 시작하지 않는다. 실행 환경을 이유로 E2E로 다시 분류하지 않는다.

   바퀴 순서는 설계안의 의존성(무엇이 무엇을 쓰는가)으로 정한다. 정책상 테스트 커밋과 구현 커밋은 같은 요구사항 범위를 다뤄야 하므로(`docs/testing/test-policy.md`), 바퀴의 요구사항 목록이 곧 두 커밋의 범위다.

4. `_workspace/00_plan.md`에 아래 형식으로 쓴다.

   ```markdown
   # 구현 계획: {슬라이스}

   ## 출처

   - 설계안: `.sdd/{슬라이스}/` (요구사항서·기능 설계서·검증 문서)
   - 요구사항 권위 출처: {Issue 번호}

   ## 바퀴

   | 바퀴 | 요구사항 ID | 시나리오 (검증 문서의 행) | 층   | 실행 환경 | 테스트 경로      | 구현 경로   | 앞 바퀴 |
   | ---- | ----------- | ------------------------- | ---- | --------- | ---------------- | ----------- | ------- |
   | K1   | R-03, R-07  | {시나리오 요약}           | Unit | jsdom     | `src/...test.ts` | `src/...ts` | 없음    |

   ## 구조 작업

   | 작업 | 완료 조건 문장 | 구현 경로   | 판정 명령           | 실행 시점 |
   | ---- | -------------- | ----------- | ------------------- | --------- |
   | S1   | {Issue 문장}   | `src/...ts` | `npm run typecheck` | K1 뒤     |

   ## 범위 밖

   - {사람 확인 시나리오 등}

   ## 계획 변경 기록

   | 날짜 | 변경 | 이유 |
   | ---- | ---- | ---- |
   ```

5. 바퀴 표를 사용자에게 보여 주고 확정받는다. 확정 전에는 2단계로 가지 않는다. 확정 뒤에 표를 바꿀 때는 `## 계획 변경 기록`에 한 행을 남긴다.

### 2단계: 바퀴 실행 (확정한 순서대로, 멈춤 조건이 없으면 쉬지 않는다)

바퀴마다 아래 ①~⑦을 순서대로 한다. 바퀴의 재시도는 이유와 상관없이 **합계 2회**다. 다음 바퀴는 다시 0부터 센다. 2회를 다 쓰고도 실패하면 멈춘다.

**① test-engineer 호출**

- `references/prompts.md`의 공통 블록과 test-engineer 블록으로 프롬프트를 만들어 `{NN}_test-engineer_prompt.md`에 저장한 뒤 부른다.
- 보고서 전문을 `{NN}_test-engineer_report.md`에 저장한다.
- `git status --porcelain -uall`로 바뀐 경로를 구한다. 모두 테스트 경로이고 이번 바퀴의 테스트 경로 안이어야 한다. 밖의 경로는 되돌리고(「되돌리기」) 재시도 1회를 써서 다시 부른다.

**② 대응표 대조**

- 보고서의 `## 대응표`에 이번 바퀴의 요구사항 ID가 모두 있는지 본다.
- 표의 테스트 이름이 실제 파일에 있는지 `grep -F`로 확인한다. 테스트 이름에 요구사항 ID가 들어 있으면 안 된다(`docs/spec/requirements.md`의 ID 규칙).
- **기대값 대조:** 테스트 파일을 직접 읽고, 테스트마다 입력과 기대값이 대응하는 요구사항 문장·시나리오 행과 맞는지 확인한다. executor는 요구사항을 보지 않으므로 테스트와 요구사항의 어긋남은 여기서 잡는다. 3단계 verifier가 다시 본다.
- 빠지거나 틀리거나 기대값이 어긋나면 근거(테스트 이름, 요구사항 문장, 어긋나는 점)를 넣어 재시도 1회를 써서 다시 부른다. 맞으면 표를 `mapping.md`에 덧붙인다.

**③ RED 확인**

- Vitest(jsdom) 환경의 Unit·Integration: `npx vitest run <이번 바퀴 테스트 파일>`을 실행한다. 이어서 `npm test` 전체에서 이번 바퀴 파일 밖의 실패가 없는지 확인한다.
- E2E 층: `npm run build`가 성공해야 한다. 이어서 `npx playwright test <이번 바퀴 테스트 파일>`을 실행한다.
- RED로 인정하는 실패:
  - 새 테스트가 기대값 불일치(assertion)로 실패한다.
  - 처음 만드는 모듈이 없어서 실패하는데, 없는 모듈이 계획의 **구현 경로**다. 그 모듈의 둘째 바퀴부터는 기대값 불일치만 인정한다.
  - E2E는 빌드가 성공한 상태에서 브라우저 검증이 실패한다.
- RED가 아닌 실패: 문법 오류, 계획 밖 모듈이 없음, 테스트 코드 자체의 타입·참조 오류, 환경 오류. 실패 출력을 넣어 재시도 1회로 다시 부른다.
- `npm run typecheck`는 계획된 구현 경로의 "모듈 없음" 오류만 허용한다. `npx eslint <테스트 파일>`과 `npx prettier --check <테스트 파일>`은 통과해야 한다.
- **새 테스트가 처음부터 통과하면 멈춘다.** 테스트를 억지로 실패하게 고치지 않는다. 바퀴 표의 세 번째 기준이 틀렸다는 뜻이고, 이 경우가 실제로 생기는지 관찰하는 중이다. 해당 테스트와 통과한 이유(어느 앞 바퀴의 구현이 만족시켰는지)를 보고한다.

**④ 테스트 커밋**

- `git add -- <경로>`로 ①에서 구한 경로만 하나씩 스테이징한다. `git add .`는 쓰지 않는다. `git diff --cached --stat`으로 테스트 경로만 있는지 확인한다.
- 메시지: `test: add failing tests for <동작>`. 테스트를 다시 고친 경우는 `test: fix tests for <동작>`이다. 제목은 소문자 영어 명령형, 72자 이하로 쓰고 요구사항 ID를 넣지 않는다. 본문 없이 마지막 문단에 `Co-Authored-By:` 트레일러만 둔다(`docs/git/commit.md`).
- 훅을 우회하지 않는다(`--no-verify` 금지). 훅이 막으면 멈추고 보고한다.

**⑤ executor 호출**

- 프롬프트는 공통 블록과 executor 블록으로 만든다. 이번 바퀴의 테스트 파일과 구현 경로만 넣는다. 요구사항 문장, 시나리오 행, 설계 문서의 경로와 내용은 넣지 않는다(「읽기 범위」).
- 보고서를 저장하고 마지막 줄의 판정을 읽는다.
  - `DONE`: ⑥으로 간다.
  - `TEST_CONFLICT`(테스트끼리 모순되거나 테스트를 고치지 않고는 통과시킬 수 없다는 보고): 아래 「테스트가 틀렸을 때」로 간다.
  - `PLAN_ISSUE`(계획 밖 파일이 필요하다는 보고): 멈추고 사용자에게 묻는다. 배치는 설계 판단이라 사용자가 정한다.
- `TEST_CONFLICT`·`PLAN_ISSUE`이면 executor가 바꾼 내용을 `git diff`와 새 파일 목록으로 `{NN}_executor.diff`에 저장한 뒤 「되돌리기」로 트리를 깨끗하게 만든다. 다음 호출이 깨끗한 트리에서 시작해야 경로 확인이 맞는다.

**⑥ 구현 확인**

- `git status --porcelain -uall`의 경로가 모두 이번 바퀴의 구현 경로 안이어야 한다. **테스트 경로가 하나라도 있으면** 그 경로를 되돌리고 재시도 1회를 써서 다시 부른다.
- 아래 「구현 확인 명령」이 모두 통과해야 한다. 실패하면 실패 출력을 넣어 재시도 1회로 다시 부른다. 구현 문제 재시도에서는 `gpt-6.1-sol`와 `high`를 명시한다.
- 보고서의 `## 실행한 명령`과 직접 실행한 결과가 다르면 직접 실행한 결과를 따르고, 차이를 `{NN}_checks.md`에 남긴다.

**⑦ 구현 커밋**

- ④와 같은 방식으로 구현 경로만 스테이징한다. 메시지: `feat: <동작>`.
- 다음 바퀴로 간다. 멈추지 않는다.

#### 구조 작업

계획의 실행 시점에 바퀴 사이에서 한다. 재시도는 작업마다 합계 2회다.

1. 공통 블록과 「executor (구조 작업)」 블록으로 프롬프트를 만든다. 완료 조건 문장과 구현 경로만 넣는다. 요구사항서·설계 문서의 경로와 내용은 넣지 않는다. 조건 문장 하나만 넘겨야 executor가 그 밖의 요구사항으로 구현을 넓히지 않는다.
2. 바뀐 경로가 그 작업의 구현 경로 안인지, 테스트 경로가 없는지 확인한다(⑥과 같음).
3. 계획의 판정 명령과 「구현 확인 명령」이 모두 통과해야 한다.
   - 2나 3에서 실패하면 위반 경로는 되돌리고(「되돌리기」), 위반 경로나 실패 출력을 재호출 사유에 넣어 다시 부른다. 재시도 1회를 쓴다. 작업의 재시도 2회를 다 쓰고도 실패하면 멈춘다.
   - `PLAN_ISSUE`면 바퀴의 ⑤와 같이 변경을 저장하고 되돌린 뒤 멈추고 사용자에게 묻는다.
4. 구현 경로만 스테이징해 커밋한다. 접두사는 변경의 성격으로 고른다(예: 위치만 옮기면 `refactor:`, 정의를 더하면 `feat:`). 동작이 바뀌지 않는 변경이라 테스트 선행의 예외다(`docs/testing/test-policy.md`).

#### 테스트가 틀렸을 때

executor가 `TEST_CONFLICT`를 내면 오케스트레이터가 근거(테스트 이름, 모순되는 단언)를 요구사항 문장과 대조해 셋 중 하나로 처리한다. executor는 요구사항을 보지 않으므로 이 판단은 오케스트레이터가 한다.

- 테스트가 요구사항과 어긋난다: 근거와 요구사항 문장을 넣어 test-engineer를 다시 부른다(재시도 1회). 아래 1~4를 따른다.
- 테스트는 요구사항대로이고 실제로 모순이다: 요구사항 자체의 문제다. 멈추고 사용자에게 묻는다.
- 모순이 아니다(executor의 오판): 왜 모순이 아닌지를 재호출 사유에 넣어 executor를 다시 부른다(재시도 1회). 요구사항 문장은 넣지 않는다.

1. 바뀐 경로가 이번 바퀴의 테스트 경로 안인지 확인한다.
2. **테스트 약화 확인:** `git diff HEAD -- <테스트 파일>`에서 지운 `it(`·`test(`·`expect(` 줄이 더한 줄보다 많으면 멈추고 사용자에게 묻는다. 테스트를 느슨하게 바꿔 통과시키는 길을 막기 위해서다.
3. ③과 같은 RED 확인을 다시 한다. 고친 테스트도 기능이 없어서 실패해야 한다. 처음부터 통과하면 멈춘다.
4. `test: fix tests for <동작>`로 커밋하고 ⑤로 돌아간다.

#### 되돌리기

각 에이전트 호출 직전 트리는 깨끗하다(직전 단계에서 커밋했으므로). 그래서 위반 경로는 아래로 되돌린다.

- 추적 중인 파일: `git restore --source=HEAD --staged --worktree -- <경로>`
- 새 파일: `git clean -f -- <경로>`

에이전트 호출 뒤 `git rev-parse HEAD`가 바뀌었거나 스테이징된 내용이 있으면, 에이전트가 커밋·스테이징한 것이다. 자동으로 되돌리지 않고 멈춘다. 커밋을 되돌리는 것은 기록을 고치는 일이라 사용자가 정한다.

#### 구현 확인 명령

명령 목록의 원본은 `.github/workflows/ci.yml`의 `npm run` 단계다. 실행할 때마다 그 파일에서 읽는다. 하네스가 목록을 복사해 두면 CI가 바뀔 때 하네스만 옛 목록으로 남는다.

- `test:e2e`는 E2E 층 바퀴와 3단계에서만 실행한다. 그 전에 `npm run build`를 실행한다.
- 직렬로 모두 실행하고, 실패해도 멈추지 않는다. 한 번에 고칠 것을 전부 보여 주기 위해서다.
- 명령과 종료 코드, 실패 출력을 `{NN}_checks.md`에 남긴다.

### 3단계: 정리와 종합 검증 (모든 바퀴가 끝난 뒤 한 번)

**정리를 마지막에 한 번만 하는 이유:** 바퀴마다 기계적 확인은 이미 했다. 정리는 구조를 다듬는 일이라 코드가 다 모였을 때 효과가 크고, 중간에 하면 다음 바퀴가 그 구조를 다시 바꿀 수 있다.

1. **code-simplifier:** 이번 실행의 구현·구조 작업 커밋들이 바꾼 경로(`git diff --name-only <시작 커밋>..HEAD`의 구현 경로)를 넣어 부른다. 바뀐 경로가 그 안에만 있는지, 「구현 확인 명령」이 모두 통과하는지 확인한다. 통과하면 `refactor: <요약>`로 커밋한다. 실패하면 정리 변경을 모두 되돌리고, 정리 없이 다음으로 간다. 최종 보고에 그 사실을 적는다. 바뀐 것이 없으면 커밋하지 않는다.
2. **verifier:** 요구사항서 경로, `00_plan.md`, `mapping.md`, 이번 실행의 커밋 목록(`git log --oneline <시작 커밋>..HEAD`)을 넣어 부른다. 판정은 `PASS`, `FAIL_TEST`(바퀴의 요구사항에 대응하는 테스트가 없거나 기대값이 요구사항과 다름), `FAIL_IMPL`(테스트는 맞는데 구현이 틀림, 또는 구조 작업의 완료 조건 미충족), `FAIL_SPEC`이다. 구조 작업은 테스트 대상이 아니므로 테스트가 없다는 이유로 `FAIL_TEST`가 되지 않는다. 이 단계에서는 재시도하지 않는다. 판정과 근거를 그대로 최종 보고에 넣는다. `FAIL_TEST`는 테스트 선행을 지키려면 바퀴를 새로 돌아야 하므로 사용자가 정한다.

### 4단계: 최종 보고

- 최종 판정과 바퀴별 결과(`run_log.md` 요약), 재시도 사용 수
- 이번 실행의 커밋 목록. push는 하지 않았다는 사실
- 요구사항 ↔ 테스트 대응표(`mapping.md`). PR `Test plan`에 옮길 때는 ID와 요구사항 문장을 함께 쓴다(`docs/spec/requirements.md`)
- 멈춤 사례와 되돌린 위반 경로
- 범위 밖 시나리오(사람 확인 등)

`_workspace/`는 사후 검증을 위해 지우지 않는다.

## 멈춤 조건

정상 흐름에서는 1단계의 확정 말고 멈추지 않는다. 아래 경우에만 멈추고 보고한다.

| 경우                                             | 이유                                                                                                                                        |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 새 테스트가 처음부터 통과                        | 테스트를 억지로 실패하게 만들지 않는다. 정책의 빈틈이 실제로 생기는지 관찰한다                                                              |
| 테스트 약화                                      | 테스트를 느슨하게 바꿔 통과시키는 것을 사람이 판단한다                                                                                      |
| 바퀴의 재시도 2회 초과                           | 더 돌려도 비용만 든다. 대개 요구사항·테스트 쪽 문제다                                                                                       |
| `PLAN_ISSUE`, 설정·문서 변경 필요, 요구사항 모호 | 에이전트가 정할 수 없는 설계 판단이다                                                                                                       |
| 에이전트가 커밋·스테이징함, 훅이 커밋을 막음     | 기록을 고치는 일은 사용자가 정한다                                                                                                          |
| 사용량 한도, 인증 만료, 권한 거부                | 다시 시도해도 같다. 재시도하지 않고, 부분 산출물과 `git status`로 실제 진행을 확인해 기록한 뒤 보고한다. 사용량 한도면 풀리는 시각도 알린다 |
| 보고서 형식 오류 2회                             | 형식만 고쳐 다시 내라는 요청은 호출당 1회이고 재시도에 세지 않는다. 이 요청 전후로 `git status`가 달라지면 경로 위반과 같이 처리한다        |

## 테스트 시나리오

### 정상 흐름

1. 작업 브랜치, 깨끗한 트리, `_workspace/` 없음. "showcase 슬라이스 구현해줘"
2. 1단계에서 K1(목록 계산, Unit)부터 K10(퇴장 중 접근성, E2E)까지 바퀴 표를 제안하고 사용자가 확정한다.
3. K1: test-engineer → 대응표 일치 → 필터 모듈 없음으로 실패(계획된 구현 경로라 RED) → `test:` 커밋 → executor `DONE` → 확인 명령 통과 → `feat:` 커밋 → K2로.
4. K10까지 같은 방식으로 진행한 뒤 code-simplifier → `refactor:` 커밋 → verifier `PASS`.
5. 결과: 테스트·구현 커밋 20개와 정리 커밋 1개, push 없음, 최종 보고.

### 오류 흐름: executor가 테스트를 고침

1. K4에서 executor가 테스트 파일의 기대값을 바꾸고 `DONE`을 낸다.
2. ⑥에서 `git status`에 테스트 경로가 보인다 → 그 경로를 되돌림 → 재시도 1 → executor 재호출.
3. 다시 고치면 재시도 2 → 다시 위반하면 멈추고 위반 경로와 함께 보고한다.

### 오류 흐름: 테스트가 처음부터 통과

1. K3의 test-engineer가 쓴 "한국어 문구" 테스트가 RED 확인에서 바로 통과한다.
2. 멈추고 보고한다. 해당 테스트, 통과 이유, 바퀴 표 수정안(이 시나리오를 앞 바퀴에 합치기)을 제시한다.

### 오류 흐름: 테스트가 틀림

1. K2의 executor가 "두 테스트가 같은 입력에 다른 순서를 기대한다"며 `TEST_CONFLICT`를 낸다.
2. executor 변경을 저장 후 되돌림 → 오케스트레이터가 요구사항 문장과 대조해 한쪽 테스트가 요구사항과 어긋남을 확인 → test-engineer 재호출(재시도 1) → 약화 확인 통과 → RED 다시 확인 → `test: fix tests for ...` 커밋 → executor 재호출.
