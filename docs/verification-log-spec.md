# 검증 로그 명세

검증 로그는 다음을 검증 한 번당 한 줄로 남긴 기록이다.

> 어떤 에이전트가, 언제, 어떤 검증(test, typecheck, lint, format:check, build)을 실행했고, 그 결과가 무엇이었는가.

이 문서는 기록의 내용, 형식, 저장 위치, 기록을 쓰는 방법을 정의한다. 각 항목에는 구현·시험 상태를 함께 적는다(아래 "구현·시험 상태").

## 범위

- 이 문서가 정하는 것: 기록 줄의 칸, 파일 구조, 검증 명령을 알아보는 규칙, 에이전트 귀속, CI 판정 규칙(설계), merge 방식(설계).
- 이 문서가 정하지 않는 것: CI 스크립트의 구현, OMC 스킬 산출물의 저장 위치, 증거 문서 템플릿, 에이전트의 다른 작업(파일 생성 등)의 기록.

## 원칙

- 기록은 LLM이 아니라 결정론적 코드(훅)가 실제 실행 결과를 그대로 적는다. 훅이 넘겨주지 않은 값은 추측해서 적지 않고, 없으면 키를 적지 않거나 `null`로 둔다.
- 기록은 검증만 남긴다. 에이전트가 검증 말고 무엇을 했는지는 적지 않는다.
- 기록은 추가 전용이다. 한 번 쓴 줄과 파일은 고치거나 지우지 않는다.
- 판정은 기계가 참/거짓을 가를 수 있는 것만 CI가 강제한다.

## 저장 구조

```
_workspace/
  verification-logs/
    <브랜치 이름의 / 를 - 로 바꾼 값>/
      <시작 시각>-<세션 ID 앞 8자>.jsonl
      verification-output/
        <세션 ID 앞 8자>-<번호>.log
```

| 요소 | 규칙 |
| ---- | ---- |
| 폴더 이름 | 브랜치 이름에서 `/`를 `-`로 바꾼 값. `feat/ch-03-newsletter`이면 `feat-ch-03-newsletter` |
| 시작 시각 | 세션 파일을 처음 만든 시각. `YYYYMMDD-HHMM` (UTC) |
| 세션 ID 앞 8자 | Claude Code 세션 ID의 앞 8자 |
| 번호 | 그 세션 안에서 세는 4자리 일련번호. `0001`부터. 출력 파일은 배타 생성하고 겹치면 번호를 올린다 |

- 세션마다 `.jsonl` 파일을 새로 만들고, 그 세션의 줄은 파일 끝에 덧붙인다.
- 서브에이전트는 부모의 세션 ID를 공유하므로 한 메인 세션의 모든 에이전트 기록이 같은 파일에 쌓인다. 에이전트는 파일이 아니라 줄의 `agent_id`, `agent_type`으로 구분한다.
- `_workspace/`는 커밋 대상이다. `.gitignore`에 넣지 않는다.

## 줄 형식

파일은 한 줄에 JSON 하나인 JSONL이다. 줄 종류는 하나뿐이다.

| 칸 | 필수 | 뜻 |
| -- | :-: | -- |
| `time` | O | 기록한 시각(검증이 끝난 직후). UTC ISO 8601, 밀리초까지 |
| `branch` | O | 브랜치 이름 전체 |
| `agent_id` | | 실행한 서브에이전트의 ID. 훅 payload에 있을 때만 적는다 |
| `agent_type` | | 실행한 서브에이전트의 종류. 훅 payload에 있을 때만 적는다 |
| `command` | O | 실행한 명령 문자열 |
| `exit_code` | O | 종료 코드. 통과/실패 판정의 유일한 근거. 중단되었거나 읽을 수 없으면 `null` |
| `head` | O | 기록 시점의 가장 최근 커밋 번호. 커밋이 없거나 읽을 수 없으면 `null` |
| `output.path` | O | 출력 원문 파일의 경로. 이 `.jsonl`이 있는 폴더 기준 상대 경로 |

```json
{"time":"2026-10-21T08:01:37.552Z","branch":"feat/verification-utils","agent_id":"a50ae0a9b3074a753","agent_type":"oh-my-claudecode:executor","command":"npm run test","exit_code":0,"head":null,"output":{"path":"verification-output/33d0c614-0003.log"}}
```

- `agent_id`와 `agent_type`은 함께 있거나 함께 없다. 둘 다 없는 줄은 서브에이전트 밖(메인 세션)에서 실행한 검증이다.
- 통과/실패를 따로 적는 칸은 없다. `exit_code`에서 계산한다.
- 개발 단계(Red/Green)와 검증 종류는 적지 않는다. 같은 `command`의 `exit_code`가 0이 아니다가 0이 되는 순서에서 읽는 쪽이 계산한다.
- `head`는 어떤 코드를 검증했는지를 가리키는 선택적 단서다. 커밋되지 않은 변경은 반영하지 않으므로 검증한 코드 자체를 특정하지 못한다.

### 적지 않는 정보

| 정보 | 적지 않는 이유 |
| ---- | -------------- |
| 줄 종류(`type`) | 줄 종류가 하나뿐이다. 종류가 늘면 그때 추가한다 |
| 세션(`session`) | 파일 이름에 있다 |
| 스크립트 이름(`script`) | `command`에서 계산된다 |
| 소요 시간(`duration_ms`) | 정의 밖이다 |
| 변경 파일 목록(`changed_files`) | 줄의 절반 이상을 차지하지만 검증한 코드를 특정하지 못한다 |
| 실행 환경(`env`) | 훅 프로세스의 값이라 검증 프로세스의 값과 다를 수 있다 |
| 출력 해시(`output.hash`) | 변조를 막는 CI가 구현될 때 추가한다 |

## 검증 명령 인식

훅은 Bash 도구 호출의 `command`가 다음 규칙에 맞을 때만 기록한다.

- 형식은 `npm run <script>` 이고, `<script>`는 다음 허용 목록 중 하나다: `test`, `test:<접미사>`(접미사는 영문·숫자·`_`·`-`이고 `:`로 여러 단계를 이을 수 있다), `typecheck`, `lint`, `format:check`, `build`.
- 파일을 고치는 스크립트(`lint:fix`, `format` 등)는 검증이 아니므로 인식하지 않는다. 고치는 스크립트에 `:fix`, `:write` 같은 접미사를 붙이고 검증 이름과 섞어 쓰지 않는다는 이름 규칙은 사람이 지키는 안내 규칙이다.
- 뒤에 `-- <인자>`를 붙일 수 있다. 인자에 셸 연결 문자(`;` `&` `|` `<` `>` `` ` `` `$` `(` `)`)가 있으면 인식하지 않는다.
- 단일 명령만 인식한다. `&&`, 파이프, 세미콜론으로 이은 복합 명령은 기록하지 않는다. 복합 명령에서는 검증의 실제 종료 코드를 훅이 알 수 없기 때문이다.
- 이 규칙에 맞지 않는 명령(`npx vitest run` 등)은 기록되지 않는다.

## 기록 방식

- `.claude/settings.json`에 등록한 `PostToolUse`(Bash)와 `PostToolUseFailure`(Bash) 훅이 `scripts/log-verification/index.ts`를 호출한다.
- 성공 이벤트면 `exit_code`는 0이고 출력은 `tool_response`의 stdout과 stderr를 이어 붙인 것이다.
- 실패 이벤트면 `exit_code`는 `error` 첫머리의 `Exit code N`에서 읽고(출력이 없으면 개행 없이 `Exit code N`만 온다), 출력은 그 부분을 뺀 나머지다.
- 중단된 호출이면 `exit_code`는 `null`이다.
- 출력 원문은 `verification-output/`에 저장하고 줄에는 경로만 적는다.
- 훅 실패는 세션을 막지 않는다. 오류는 표준 에러로만 출력한다.

## 구현·시험 상태

| 항목 | 상태 |
| ---- | ---- |
| 훅 기록(`log-verification.ts`) | 구현됨. 실제 세션에서 서브에이전트(`test-engineer`, `executor`, `verifier`)와 메인 세션이 실행한 `npm run test`·`typecheck`가 기록됨. 가짜 payload로 허용 목록, 복합 명령 제외, 출력 없는 실패, 중단을 추가로 시험함 |
| 훅의 자동 시험 | 없음 |
| 서브에이전트의 검증 줄 | 실측함. `agent_id`, `agent_type`이 줄에 직접 적히고 서로 다른 ID로 구분됨. 실패(`exit_code: 1`) 후 통과(`0`) 흐름도 줄 순서로 읽힘 |
| 메인 세션의 검증 줄 | 실측함. 성공 2건(`npm run test`, `npm run typecheck`)과 실패 1건(`npm run test -- zzz-no-such-file`, `exit_code: 1`)이 `agent_id`, `agent_type` 키 없이 기록됨. 서브에이전트 줄과 같은 파일에 시간순으로 섞여 쌓임 |
| `lint`, `format:check`, `build` | 해당 스크립트가 `package.json`에 없어 기록된 적 없음 |
| 중단된 호출의 `exit_code: null` | 실제 세션에서 관측한 적 없음(가짜 payload로만 시험) |
| 출력이 없는 실패의 `exit_code` | 실제 세션에서 관측한 적 없음(가짜 payload로만 시험) |
| 동시에 실행되는 에이전트 | 시험한 적 없음 |
| CI 판정 규칙, merge commit | **설계만 있고 구현되지 않음.** `.github/`가 없음 |
| `head` | 커밋이 없는 저장소라 지금까지 모든 줄이 `null` |

## CI 판정 규칙 (설계, 미구현)

CI는 기록을 쓰지 않고 판정만 한다. 코드의 통과 여부는 CI가 검증을 다시 실행해 판정한다.

| # | 규칙 | 실패 조건 |
| -- | ---- | -------- |
| 1 | 기록 폴더의 기존 파일을 보존한다 | PR이 `_workspace/verification-logs/` 아래 기존 파일을 수정, 삭제, 이름 변경함 |
| 2 | `src/`를 바꾼 PR은 기록을 남긴다 | PR이 `src/` 아래를 바꿨는데, PR이 추가한 `.jsonl` 파일에 유효한 줄이 하나도 없음 |

유효한 줄은 JSON으로 읽히고, 위 표의 필수 칸(`time`, `branch`, `command`, `exit_code`, `head`, `output.path`)이 모두 있으며 타입이 맞는 줄이다. `time`은 ISO 8601 문자열, `exit_code`는 정수 또는 `null`, `head`는 문자열 또는 `null`이다. `agent_id`와 `agent_type`이 있으면 둘 다 문자열이어야 한다.

- `src/` 밖만 바꾼 PR에는 규칙 2를 적용하지 않는다.
- 테스트 파일은 `src/` 안에 둔다. 테스트만 고친 PR도 규칙 2의 대상이다.
- 이 규칙은 앞으로 올라오는 PR에만 적용한다. 과거 코드에는 소급하지 않는다.

## merge 방식 (설계, 미적용)

작업 브랜치 PR은 merge commit으로 합친다. 기록의 `head`가 기본 브랜치 이력에서도 유효해야 하기 때문이다. 전역 `GIT.md`의 squash merge 규칙을 이 저장소에서만 대체한다. 저장소에는 아직 커밋이 없어 적용된 바 없다.

## 제약 대응표

| 제약 | 충족하는 항목 | 상태 |
| ---- | ------------- | ---- |
| 결정론적 코드가 실제 결과를 적는다 | 훅 기록, `exit_code`, 훅이 주지 않은 값은 적지 않는 원칙 | 구현·실측됨 |
| 로컬에서 생성하고 저장소에 커밋한다 | 저장 구조, `_workspace/` 커밋 | 생성은 구현됨, 커밋은 하지 않음 |
| 실패 → 수정 → 통과 흐름이 남는다 | 검증 실행마다 한 줄, 추가 전용 | 실측됨(`test`: 1, 1, 0) |
| 어떤 에이전트가 실행했는가 | `agent_id`, `agent_type` (훅 payload에서 직접) | 서브에이전트에서 실측됨. 메인 세션은 두 키가 없는 줄로 실측됨 |
| 어떤 코드에 대한 검증인가 | `head` | 한계 있음(아래), 모든 값이 `null` |
| 증거는 저장소 문서다 | 저장 구조 | 구조는 구현됨 |
| 사후 변조를 막는다 | CI 규칙 1, merge commit | **미구현** |

## 한계

- 이 기록은 **검증이 돌았다는 긍정 증거**로만 쓸 수 있다. 검증을 안 돌린 경우, 복합 명령으로 돌린 경우, 허용 목록 밖 명령으로 돌린 경우, 훅이 오류로 기록하지 못한 경우가 모두 "줄 없음"으로 보여서 서로 구별되지 않는다.
- 훅은 세션 ID가 없거나 분리된 HEAD이거나 git 오류가 나면 줄을 쓰지 못한다. 오류는 표준 에러로만 나오고 기록에는 흔적이 없다.
- 에이전트 신원은 훅 payload에 `agent_id`가 있을 때만 적힌다. 메인 세션의 검증은 신원 키가 없다.
- 인식 규칙에 맞는 단일 `npm run` 명령만 기록한다. 다른 방식으로 돌린 검증은 기록되지 않는다.
- 성공한 호출은 종료 코드 필드가 없어 0으로 간주한다. 출력은 stdout과 stderr를 이어 붙이므로 둘이 번갈아 나온 순서는 보존되지 않는다.
- `exit_code: null`은 중단된 호출이거나 `Exit code` 문구를 읽지 못한 경우다. 둘을 구별하지 못한다.
- `head`는 커밋되지 않은 변경을 반영하지 않는다. 검증한 코드를 특정하지 못한다. 지금은 커밋이 없어 모두 `null`이다.
- CI는 기록이 훅이 쓴 것인지 확인하지 않는다(CI 자체가 미구현이다). 형식만 맞춘 손으로 쓴 줄은 통과한다.
- 늦게 만든 기록은 통과 줄만 남는다. 과정이 없다는 것은 기록 내용을 읽어야 알 수 있다.
- 개발 단계(Red/Green)는 저장하지 않는다. 시스템이 결정론적으로 알려주는 값을 찾지 못했다.
- 이미 merge된 세션 파일에 줄을 더하면 규칙 1에 걸린다.
- 이 문서는 코드를 에이전트가 썼는지는 증명하지 않는다. 증명하는 것은 검증이 실행되었다는 사실이다.

## 보류

- CI 규칙의 구현과 출력 해시(`output.hash`)의 재도입.
- CI 실패 횟수를 세어 루프를 멈추고 그 사실을 기록하는 제어기.
- 역할별 필수 검증 표(`test-engineer`는 test만, `executor`는 전체 등)와 이를 CI가 판정하는 규칙.
- 검증한 코드를 특정하는 방법(내용 지문 등). 정의에 "어떤 코드에 대해"를 넣기로 하면 다시 다룬다.
- `SubagentStop` 훅으로 종료를 막는 강제. 문서는 가능하다고 하나 백그라운드 에이전트에서의 시험은 막히지 않았다.
