# 디자인 문서

도메인 설계 문서의 구성과 모든 도메인이 따르는 규칙을 둔다. 도메인은 페이지 슬라이스 하나다. 한 슬라이스의 라우트는 모두 한 도메인이다.

## 판단 기준

- 도메인마다 디자인 기준이 달라 사이트 공통 디자인 기준을 두지 않는다. 공통으로 두는 것은 문서의 구성과 구현 규칙이다.
- 항상 알아야 할 공통 내용은 이 README에, 조건부 공통 규칙은 `*-policy.md`에, 도메인마다 달라지는 내용은 도메인 설계 문서에 둔다.
- 설계 문서는 설계안이다. 무엇을 어디에 어떻게 만들지 쓴다.
- 구현 세션은 원본 디자인을 보지 않는다. 설계안과 `theme.css`만으로 구현을 끝낼 수 있어야 한다.
- 챌린지 화면에는 쇼케이스 공통 요소를 두지 않는다. 원본 재현이 챌린지의 목적이기 때문이다.

| 도메인 종류     | 라우트        | 디자인 기준                  |
| --------------- | ------------- | ---------------------------- |
| 쇼케이스 페이지 | `/`           | 직접 정한다                  |
| 챌린지 페이지   | `/<슬라이스>` | 과제와 원본 디자인을 분석한다 |

## 문서

| 문서 | 읽는 조건 | 다루는 내용 |
| --- | --- | --- |
| [`component-policy.md`](component-policy.md) | 컴포넌트를 설계하거나 구현할 때 | shadcn/ui 사용, 직접 제작 기준, 포커스 표시 |
| [`theme-policy.md`](theme-policy.md) | `theme.css`를 만들거나 구현에서 시각 값을 쓸 때 | 구현 방식, 산출 규칙, 산출 순서, 사용 규칙, 다크 모드, 폰트, Portal |

## 설계 문서 구성

도메인마다 아래 문서를 만든다.

| 문서 | 답하는 질문 | 다루는 내용 |
| --- | --- | --- |
| `requirements.md` | 무엇을 만드나 | 기본 정보, 사용자가 끝내야 하는 일, 기능 요구사항, 범위 밖, 판단 우선순위, 원본과 다른 점 |
| `behavior.md` | 조건마다 어떻게 동작하나 | 화면 상태, 입력과 결과 |
| `layout.md` | 화면을 어떻게 나누나 | 화면 영역, 반응형, 상태별 배치 |
| `content.md` | 화면에 무엇을 쓰나 | 표기 규칙, 영역별 문구, 상태 문구 |
| `components.md` | 무엇을 어디에 만드나 | 컴포넌트 구성, 컴포넌트 트리, 상태 표현 |
| `data.md` | 어떤 데이터를 어떻게 쓰나 | 데이터 형태, 위치, 함수 |
| `ui.md` | 어떻게 표현하나 | 배경, 표면, 크기, 스크롤, 애니메이션 규칙 |

## 작성 순서

1. `requirements.md`, `behavior.md`를 쓴다.
2. `layout.md`, `content.md`를 쓴다.
3. `components.md`, `data.md`를 쓴다.
4. `ui.md`와 `theme.css`를 만든다.
5. 구현 세션은 도메인의 첫 구현에서 `theme.css`를 슬라이스로 복사한다. 이후 기준은 `src/`의 파일이다.

## 산출 위치

```
.sdd/<도메인>/design/
├── requirements.md
├── behavior.md
├── layout.md
├── content.md
├── components.md
├── data.md
├── ui.md
└── theme.css
```

- `<도메인>`은 슬라이스 이름과 같게 쓴다.
- 슬라이스 이름은 설계를 시작할 때 정한다.
- `.sdd/`는 구현 전 작업 자료라서 저장소에 남기지 않는다.
- 원본 디자인 파일은 두지 않는다. 분석한 설계안만 둔다.
- 새 worktree에는 `.sdd/`가 없다. 구현 세션에는 메인 체크아웃의 경로를 직접 알려준다.

## 작성 규칙

- 문서를 지우지 않는다. 모든 도메인의 구성을 같게 유지해야 도메인끼리 비교할 수 있다.
- 내용이 없으면 "해당 없음"으로 쓴다.
- 원본에서 분석한 문구, 배치, 상태는 구체적으로 쓴다.
- 시각 값은 `theme.css`에만 둔다. 설계와 구현이 같은 내용이라 문서로 쓰지 않는다.
- 어디에 어떤 표현을 쓰는지는 `ui.md`에 쓴다. 값이 아니라서 `theme.css`로 표현할 수 없다.
- 설계안에서 시각 값이 필요한 자리는 토큰이나 페이지 변수 이름으로 가리킨다. 구현 세션이 어느 값을 어디에 쓸지 추측하지 않게 하기 위해서다.
- 원본과 과제로 답이 나오지 않는 판단은 지어내지 않는다. `(미결정)`으로 두고 사용자에게 묻는다.
- 구현은 `(미결정)`이 없고 `theme.css`가 준비된 뒤에 시작한다.
- 판단이 충돌하면 `requirements.md`의 판단 우선순위에서 위의 항목을 따른다.
- `layout.md`의 화면 영역은 위에서 아래 순서로 쓴다.
- 모든 문서의 화면 자리는 `layout.md`의 영역 이름을 쓴다.
- 컴포넌트 트리는 페이지 컴포넌트부터 쓴다.
- 구현에 영향을 준 판단은 PR 본문에 옮긴다. `.sdd/`는 저장소에 남지 않아서 PR이 판단의 근거가 된다.
- 컴포넌트를 직접 만든 사유는 PR 본문에 쓰지 않아도 된다.
- 챌린지는 PR merge 전에 사용자가 원본과 화면을 비교하고 결과를 PR Test plan에 남긴다. 시각 일치는 테스트로 검증하지 않기 때문이다.
