# 보고서 형식

Discord로 보낼 본문을 쓸 때 읽는다. 종류가 다른 보고서들이 같은 채널에 섞이므로 서식을 한 군데 둔다.

예시의 작업명·번호는 형식 설명용 가상 값이다.

---

## 종류

| 종류       | 이모지 | 쓰는 때                             |
| ---------- | ------ | ----------------------------------- |
| 오늘 목록  | 📋     | 오늘 할 작업의 상태 라벨이 바뀜     |
| Issue 닫힘 | ✅     | Issue 하나가 닫힘                   |
| 일일 회고  | 🌙     | 하루가 지남                         |

읽는 사람이 이모지로 종류를 먼저 가르므로 한 종류에 두 이모지를 쓰지 않고, 종류가 늘면 이 표에 먼저 더한다.

## 제목 줄

첫 줄은 아래로 고정한다. 여러 저장소가 같은 채널에 보고하므로, 읽는 사람이 이 줄의 종류·저장소·날짜로 메시지를 구분한다.

```
## 📋 <repo> · 2026-01-15 KST
```

이모지는 위 "종류" 표에서 고른다. 날짜는 한국 시간 기준이다. `<repo>`는 저장소 이름이고 owner는 뺀다. 저장소들이 모두 같은 계정이라 owner는 구분에 보탬이 없고 제목만 길어진다.

## 본문 모양

- 제목 줄과 본문, 섹션 사이, 섹션 제목과 목록 사이에는 빈 줄을 하나 둔다. 섹션 제목은 `**굵게**`로 쓴다.
- 항목은 `-` 목록으로 쓰고 작업명은 `**굵게**`로 강조한다. 이슈 번호와 링크는 강조하지 않는다.
- 작업명은 Issue 제목에서 종류 접두사(`feat: `, `fix: `, `chore: ` 등)를 뗀 나머지다. 접두사가 가리키는 카테고리는 섹션 제목이나 뒤에 붙는 표시로 이미 보인다.
- PR 제목은 접두사를 떼지 않는다. PR에는 카테고리 표시가 따로 없어 접두사가 유일한 종류 단서다.
- 이모지는 제목과 표시 어휘에만 쓴다. 장식용 구분선이나 인용 블록은 쓰지 않는다.
- 이슈·PR 링크는 `[#번호](<https://...>)`처럼 번호에 건다. 긴 URL을 본문에 따로 표시하지 않고, URL은 꺾쇠로 감싸 미리보기 카드를 억제한다. 관계 안내에서 번호를 다시 언급할 때는 일반 텍스트로 쓴다.
- 항목이 없는 섹션은 쓰지 않는다.
- 표는 쓰지 않는다. Discord에서 렌더링되지 않는다.
- 한 메시지는 2000자 이하로 쓴다. 넘으면 요약해서 줄인다. 전송 쪽은 초과한 본문을 보내지 않는다.

## 📋 오늘 목록

오늘 목록의 알림이다. 목록은 상태 라벨(`SELECTED`·`IN_PROGRESS`)이 붙은 열린 Issue 전체이고, 원본은 라벨이다. 작업은 사용자가 고른다. 에이전트가 더하거나 빼지 않는다.

항목과 표시 어휘는 [`classification.md`](../../.claude/skills/todo-orchestrator/references/classification.md)가 정한다. 이 절은 그 어휘를 어디에 놓을지만 정한다.

- 섹션은 카테고리다. 섹션 순서는 `classification.md` "카테고리", 항목 순서는 "결과 순서"를 따른다.
- 상태 표시는 작업명 뒤에 가운뎃점(`·`)을 앞뒤 공백과 함께 두고 이어 붙인다. 관계 줄과 같은 줄에 두지 않는다.
- 관계 어휘는 항목 바로 아래 줄에 두 칸 들여 쓴다. 열린 직접 선행이 없으면 줄을 생략한다. 일반 선행은 한 줄, 상위 묶음은 `← #19` 다음 줄에 두 칸 더 들여 `└─ #29, #30 남음`을 더해 두 줄이다.
- 상위 묶음이 여러 개면 묶음마다 두 줄을 반복하고, 일반 선행은 한 줄로 묶어 따로 쓴다. 줄 순서는 각 줄 또는 묶음의 첫 번호순이다.
- 역방향 어휘(`🔓 끝내면…`)와 그 항목 자신의 `⬆ 상위…`는 쓰지 않는다. 메시지에는 선행 방향만 둔다.
- 관계 줄의 번호는 일반 텍스트로 쓴다. 링크는 항목 번호에만 건다.
- 관계 줄 아래에 트리나 코드블록을 더하지 않는다.

```
## 📋 <repo> · 2026-01-15 KST

**feature**

- [#101](<https://github.com/<owner>/<repo>/issues/101>) **로그인 폼 유효성 검사**
- [#102](<https://github.com/<owner>/<repo>/issues/102>) **목록 페이지 로딩 상태 표시**
  ← #101
- [#104](<https://github.com/<owner>/<repo>/issues/104>) **인증 오류 메시지 연결** · 🔄 진행 중
  ← #101
- [#105](<https://github.com/<owner>/<repo>/issues/105>) **인증 오류 처리**
  ← #100
    └─ #101, #104 남음

**other**

- [#103](<https://github.com/<owner>/<repo>/issues/103>) **CI 캐시 설정**
```

## ✅ Issue 닫힘

닫힌 Issue 하나의 보고다. 제목 줄 다음 줄에 그 Issue를 쓰고, 나머지는 섹션으로 둔다.

- Issue 줄은 `-` 목록으로 쓰지 않는다. 항목이 하나뿐이라 목록은 없는 구조를 주장한다.
- Issue 줄의 표시는 작업명 뒤에 가운뎃점으로 이어 붙인다. 순서는 카테고리, 닫힘 사유다. 카테고리는 `classification.md` "카테고리"에서 고른다.
- 닫힘 사유는 완료면 `완료`, 하지 않기로 한 것이면 `하지 않음`이다. GitHub의 닫힘 사유를 그대로 옮기고 추론하지 않는다.
- **요약** 섹션은 무엇이 해결되었는지 한두 줄이다. 연결된 PR이 있으면 마지막 항목으로 PR 번호를 건다. 해결 과정, 설계 근거, 검증 결과는 쓰지 않는다.
- **뱃지** 섹션은 떼어낸 상태 라벨을 쓴다. 뗀 라벨이 없으면 섹션을 쓰지 않는다.
- 닫힌 Issue가 blocking하던 Issue는 쓰지 않는다. 막힘 해소는 다음 오늘 목록 보고에서 선행 줄이 사라지는 것으로 보인다.

```
## ✅ <repo> · 2026-01-15 KST

[#101](<https://github.com/<owner>/<repo>/issues/101>) **로그인 폼 유효성 검사** · bug · 완료

**요약**

- 빈 입력과 형식 오류를 제출 전에 막는다
- PR [#108](<https://github.com/<owner>/<repo>/pull/108>)

**뱃지**

- `SELECTED` 떼어냄
```

## 🌙 일일 회고

하루 사이에 끝난 것의 보고다. 섹션은 아래 순서로 둔다.

- **닫은 Issue** — 항목은 `#번호 작업명`에 카테고리를 가운뎃점으로 이어 붙인다. 하지 않기로 닫은 것은 `하지 않음`을 더 붙인다. 번호순이다.
- **머지한 PR** — 항목은 `#번호 PR 제목`이다. 번호순이다.
- **하루 요약** — 목록에서 읽어낼 수 없는 것만 한두 줄로 쓴다. 항목 수를 다시 세거나 목록을 문장으로 옮겨 적지 않는다.

조회한 창구 밖의 Issue·PR은 넣지 않는다. 닫은 Issue와 머지한 PR이 모두 없으면 보고를 보내지 않는다. 조용한 하루를 알릴 내용이 없고, 매일 오는 빈 보고는 읽히지 않는다.

```
## 🌙 <repo> · 2026-01-15 KST

**닫은 Issue**

- [#101](<https://github.com/<owner>/<repo>/issues/101>) **로그인 폼 유효성 검사** · bug
- [#103](<https://github.com/<owner>/<repo>/issues/103>) **CI 캐시 설정** · other · 하지 않음

**머지한 PR**

- [#108](<https://github.com/<owner>/<repo>/pull/108>) **feat: 로그인 폼 유효성 검사**

**하루 요약**

인증 흐름의 입력 검증까지 끝냈다. 오류 메시지 연결은 아직 남았다.
```
