# docs 작성 기준

`docs/`는 AI 에이전트가 시스템에서 읽어낼 수 없는 판단 기준만 담는다.

## 용어

원리는 [프로젝트 README](../README.md#기준과-검증)에 있다. 이 문서는 아래 용어로 쓴다.

| 용어      | 뜻                                                                    |
| --------- | --------------------------------------------------------------------- |
| 설정      | 기계가 읽고 판정하는 기준. 설정 파일과 저장소 설정(GitHub)            |
| 검증 코드 | 판정 로직 자체. 테스트와 로컬 git 훅                                  |
| CI        | 설정과 검증 코드를 언제, 어디서 실행할지 정한다                       |
| 문서      | 기계가 판정할 수 없는 기준. 이유, 예외, 판단 기준. 이 `docs/`가 담는다 |

## 무엇을 두는가

| 둔다 (읽어낼 수 없다)                                      | 두지 않는다 (읽어낼 수 있다)                               |
| ---------------------------------------------------------- | ---------------------------------------------------------- |
| 이유, 트레이드오프, 선택 기준                              | 실행 명령, 스크립트 표 (`package.json`)                    |
| 예외와 "이 경우엔 이렇게 판단한다"                         | 버전, 의존성 목록 (`package.json`)                         |
| 설정과 검증 코드로 판정되지 않는 규칙                      | 판정 규칙의 나열 (`steiger.config.js`, `eslint.config.js`) |
| 저장소 파일로 확인되지 않는 설정 (예: GitHub 저장소 설정)  | CI 단계 (`.github/workflows/ci.yml`)                       |
| 어디에 둘지 정하는 구조의 의미 (예: 레이어별 역할)         | 디렉토리 목록 그 자체                                      |

시스템이 이미 정의하는 내용은 다시 쓰지 않고 그 파일을 가리킨다.

## 리뷰 기준

`docs/`의 문서를 리뷰할 때 쓰는 기준이다. 리뷰어는 위반을 ID로만 보고한다. 표에 없는 기준으로는 지적하지 않고, 필요하면 표에 먼저 추가한다.

항목은 표 행 하나, 불릿 하나, 문장 하나다. 판정은 파일이나 제목이 아니라 항목 단위로 한다.

| ID  | 판정 질문                                                                                                                  | 위반 시 조치                                   | 판정                                                       |
| --- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| D1  | 설정 파일과 코드만으로 에이전트가 같은 판단을 내릴 수 있는 항목이 남아 있는가? (실행 명령, 버전, CI 단계, 판정 규칙 나열 포함) | 삭제하거나 해당 파일 경로로 바꾼다             | 리뷰 (명령·버전·CI 단계는 문자열 검색으로 기계 판정 가능)  |
| D2  | 한 항목이 한 가지 주장만 담는가?                                                                                           | 둘로 쪼갠다. 조각의 답이 모두 같아지면 멈춘다  | 리뷰                                                       |
| D3  | 각 디렉토리 `README.md`의 인덱스 표가 그 디렉토리의 실제 문서와 일치하는가?                                                | 표나 문서를 맞춘다                             | 기계 (미구현)                                              |
| D4  | `AGENTS.md` Context 행이 실제 `docs/` 문서와 일치하는가?                                                                   | 행이나 문서를 맞춘다                           | 기계 (미구현)                                              |
| D5  | 문서 안의 상대 링크와 앵커가 유효한가?                                                                                     | 링크를 고친다                                  | 기계 (미구현)                                              |
| D6  | `assurance/README.md`의 규칙(문항 동결, 체크박스 금지, 포인터만 보유)을 지켰는가?                                           | 되돌린다                                       | 리뷰                                                       |

- 보고 형식은 `파일 | 항목 | ID | 판정 | 조치`다. 요약은 섹션별로 먼저 쓰고, 판정은 항목 단위로 한다.
- 기계로 판정되는 D3~D5가 검사 스크립트로 올라가면 이 표의 판정 열을 `기계 (구현됨)`으로 고친다.

## 한계

항목의 경계와 "읽어낼 수 있는가"는 의미 판단이라 자동으로 검사되지 않는다. 리뷰가 [리뷰 기준](#리뷰-기준)으로 확인한다.
