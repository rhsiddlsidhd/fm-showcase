# docs 작성 기준

`docs/`는 AI 에이전트가 시스템에서 읽어낼 수 없는 판단 기준만 담는다.

## 용어

원리는 [프로젝트 README](../README.md#기준과-검증)에 있다. 이 문서는 아래 용어로 쓴다.

| 용어      | 뜻                                                                    |
| --------- | --------------------------------------------------------------------- |
| 설정      | 기계가 읽고 판정하는 기준. 설정 파일과 저장소 설정(GitHub)            |
| 검증 코드 | 판정 로직 자체. 테스트와 로컬 git 훅                                  |
| CI        | 설정과 검증 코드를 언제, 어디서 실행할지 정한다                       |
| 문서      | 기계가 판정할 수 없는 기준. 이유, 예외, 판단 기준. 이 `docs/`가 담는다 |

## 무엇을 두는가

| 둔다 (읽어낼 수 없다)                                      | 두지 않는다 (읽어낼 수 있다)                               |
| ---------------------------------------------------------- | ---------------------------------------------------------- |
| 이유, 트레이드오프, 선택 기준                              | 실행 명령, 스크립트 표 (`package.json`)                    |
| 예외와 "이 경우엔 이렇게 판단한다"                         | 버전, 의존성 목록 (`package.json`)                         |
| 설정과 검증 코드로 판정되지 않는 규칙                      | 판정 규칙의 나열 (`steiger.config.js`, `eslint.config.js`) |
| 저장소 파일로 확인되지 않는 설정 (예: GitHub 저장소 설정)  | CI 단계 (`.github/workflows/ci.yml`)                       |
| 어디에 둘지 정하는 구조의 의미 (예: 레이어별 역할)         | 디렉토리 목록 그 자체                                      |

시스템이 이미 정의하는 내용은 다시 쓰지 않고 그 파일을 가리킨다.

## 리뷰 기준

`docs/`의 문서와 `adr/`의 기록을 리뷰할 때 쓰는 기준이다. 리뷰어는 위반을 ID로만 보고한다. 표에 없는 기준으로는 지적하지 않고, 필요하면 표에 먼저 추가한다.

항목은 표 행 하나, 불릿 하나, 문장 하나다. 판정은 파일이나 제목이 아니라 항목 단위로 한다.

| ID  | 판정 질문                                                                                                                       | 위반 시 조치                                  | 판정 |
| --- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ---- |
| D1  | 설정 파일과 코드만으로 에이전트가 같은 판단을 내릴 수 있는 항목이 남아 있는가? (실행 명령, 버전, CI 단계, 판정 규칙 나열 포함) | 삭제하거나 해당 파일 경로로 바꾼다            | 리뷰 |
| D2  | 한 항목이 판정을 따로 받아야 하는 규칙을 둘 이상 담는가? 규칙과 그 이유, 규칙과 그 예외는 한 주장으로 본다. 섹션·필드를 나열한 표 행은 목록이므로 대상이 아니다 | 규칙마다 항목을 나눈다. 나눈 항목들이 D1~D11에서 모두 같은 판정을 받으면 나누지 않는다 | 리뷰 |
| D3  | 각 디렉토리 `README.md` 인덱스 표의 "다루는 내용"에 적힌 주제가 문서에 있고, 문서의 주제가 빠짐없이 적혀 있는가? 주제 단위의 불일치는 D3, 주제 안의 판단 공백은 D9다 | 표나 문서를 맞춘다 | 리뷰 |
| D4  | `AGENTS.md` Context의 "다루는 내용"이 실제 `docs/` 문서와 맞는가? 행의 대상은 `docs/` 바로 아래의 문서와 하위 디렉토리 인덱스다 | 행이나 문서를 맞춘다 | 리뷰 |
| D5  | `docs/`, `AGENTS.md`, `README.md` 안의 저장소 내부 링크와 백틱 경로에 대해, 링크 설명이나 앞뒤 문장이 말하는 내용이 대상에 있는가? 외부 URL은 대상의 제목이 설명과 맞는지만 본다 | 링크나 경로를 고친다 | 리뷰 |
| D6  | `interview/README.md`의 "규칙" 절을 어긴 항목이 있는가? | 문항지 변경과 문항지 외 파일은 되돌린다. 답을 남기는 위치를 어긴 항목은 그 규칙이 정한 위치로 옮긴다 | 리뷰 |
| D7  | D1에 해당하지 않으면서, 지워도 에이전트의 판단이나 행동이 달라지지 않는 항목이 남아 있는가? (도구나 일반 원칙의 설명 포함) 규칙의 적용 범위를 정하거나 결정을 설명하는 이유는 대상이 아니다 | 삭제한다 | 리뷰 |
| D8  | 같은 규칙이나 정의가 `docs/`, `AGENTS.md`, `README.md` 안의 다른 문서에도 있는가? (표현이 달라도 같은 판단을 요구하면 같다. `adr/`의 결정 기록과 인덱스 표의 "다루는 내용"은 대상이 아니다) | 읽는 조건이 그 대상을 다루는 문서 하나에만 두고, 나머지는 그 문서 링크로 바꾼다 | 리뷰 |
| D9  | 다음 중 하나가 있는가? ① 문서의 읽는 조건에 해당하는 작업 중, 이 문서의 규칙으로는 결론이 둘 이상 나오는 구체적 경우 ② 두 항목이 같은 대상에 서로 다른 판단을 요구하는 경우 ③ 문서가 판단을 정해 두었는데, 그 판단이 필요한 작업이 읽는 조건에 빠져 있는 경우 | 규칙을 추가하거나 읽는 조건을 고친다. 충돌이면 한쪽을 고치거나 예외임을 명시한다. 위반은 결론이 갈리는 경우를 함께 적는다 | 리뷰 |
| D10 | 설정이나 검증 코드로 판정되게 만들 수 있는데, 판정되지 않는 이유 없이 문서에만 있는 항목이 있는가? | 설정이나 검증 코드로 올리고 문서에서 지운다. 올리지 못하면 판정되지 않는 이유를 항목 옆에 쓴다([`architecture/README.md`](architecture/README.md#설정과-문서)의 표 형식) | 리뷰 |
| D11 | `adr/`의 기록이 [`spec/adr.md`](spec/adr.md)의 쓰는 조건, 섹션과 분량, 출처 규칙을 지켰는가? | merge 전이면 고친다. merge된 기록은 고치지 않고 새 ADR로 대체한다 | 리뷰 |

- 보고 형식은 `파일 | 항목 | ID | 판정 | 조치`다. 요약은 섹션별로 먼저 쓰고, 판정은 항목 단위로 한다.
- 보고에는 검사 범위(읽은 파일 수, 확인한 링크 수, 비교한 인덱스 표 수)를 함께 쓴다. 위반이 없다는 보고는 범위가 있어야 확인할 수 있다.
- 링크·앵커·백틱 경로가 존재하는지, 인덱스 표의 행과 파일 목록이 일치하는지는 검증 코드가 판정한다. 검증 코드가 생기기 전까지는 리뷰가 확인한다.
- 리뷰는 위 표의 기준으로 뜻이 맞는지를 판정한다.

## 한계

항목의 경계와 "읽어낼 수 있는가"는 의미 판단이라 자동으로 검사되지 않는다. 리뷰가 [리뷰 기준](#리뷰-기준)으로 확인한다.
