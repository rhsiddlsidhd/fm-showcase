# 자료구조와 알고리즘 선택

자료구조나 알고리즘을 선택할 때는 먼저 함수가 수행하는 일을 분명히 한다. 이름이나 익숙함만으로 구현 방식을 고르지 않는다.

## 판단 순서

1. **문제의 형태를 정한다.** 조회, 분류, 탐색, 변환, 집계 중 무엇인지 확인한다.
2. **입력과 사용 빈도를 확인한다.** 입력 크기가 커질 수 있는지, 데이터가 고정인지 동적인지, 함수가 반복 호출되는지 살핀다.
3. **요구되는 동작을 보존한다.** 경계값, 누락값, 잘못된 입력, 기본값 처리와 반환값의 의미를 정한다.
4. **요구사항에 맞는 표현을 고른다.** 복잡도 차이가 입력 규모와 호출 빈도에서 성능 요구에 영향을 주는지 확인한다. 요구되지 않은 최적화나 추상화는 추가하지 않는다.
5. **시간·공간 복잡도를 설명한다.** 지배하는 입력 크기를 밝히고, 초기 구성 비용과 호출당 비용을 구분한다.

## 흔한 선택

| 문제 | 먼저 고려할 표현 | 주의할 점 |
| ---- | ---------------- | -------- |
| 고정된 키에서 값을 찾음 | 객체 또는 `Map` 조회 | 키의 형태, 누락 키 처리, 데이터 변경 여부에 맞춰 고른다 |
| 항목 수가 고정된 목록을 범주별로 분류 | 범주와 값 목록을 선언하고 `find`로 검색 | 항목 수가 바뀌거나 커질 때 순회 비용을 다시 평가한다 |
| 경우마다 다른 동작을 수행 | `switch` 또는 조건문 | 범위 조건이 유효하지 않은 값까지 받아들이지 않는지 확인한다 |
| 정렬된 데이터에서 반복 탐색 | 정렬과 이진 탐색 등 탐색 구조 | 정렬 비용과 데이터 갱신 비용을 포함해 비교한다 |

표는 기본 출발점이지 강제 규칙이 아니다. 입력 크기, 갱신 방식, 호출 빈도와 성능 요구사항을 함께 고려한다.

## 복잡도와 비용

- 목록의 항목 수가 고정되어 있으면 순회는 항목 수에 비례한다. 검색 입력의 크기와 무관하게 항목 수가 일정하므로, 이 순회는 검색 입력 크기 기준으로 상수 시간이다. 항목 수가 커지거나 실행 측정에서 검색 비용이 성능 요구에 영향을 주면 조회 구조를 비교한다.
- 데이터 준비 비용과 실제 함수 호출 비용을 따로 본다. 예를 들어 목록을 객체로 한 번 펼치는 방식은 초기화 비용과 조회 비용이 다르다.
- 시간 복잡도는 입력 크기가 증가할 때의 증가율을 비교한다. 항목 수가 고정된 목록의 순회 비용은 해당 목록의 항목 수에 의해 제한된다.
- 메모리 사용량과 구현 복잡도도 함께 본다. 빠른 조회를 위해 중복 자료나 별도 변환 단계를 추가할 이유가 있는지 확인한다.
- 여러 구현이 요구사항을 만족하면, 데이터 크기와 갱신 방식, 호출 패턴에 맞는 구현을 선택한다.

## 예: 코드에서 아이콘 분류

날씨 코드처럼 항목 수가 고정된 코드 집합을 여러 아이콘 범주로 분류한다면, 범주별 코드 목록을 한곳에 선언하고 일치하는 범주를 찾는 방식을 사용할 수 있다. 매핑이 누락된 경우의 기본 아이콘도 반환 지점에서 명시한다. 항목 수가 바뀌거나 실행 측정에서 조회 비용이 성능 요구에 영향을 주면 객체나 `Map`을 검토한다.
