# 요구사항서

요구사항서는 Issue가 정한 문제를 구현 전에 확인할 수 있는 동작으로 나눈 설계안이다. 도메인마다 `.sdd/<슬라이스>/requirements.md`에 둔다.

요구사항의 권위 출처와 테스트 대응을 남기는 곳은 [`test-policy.md`](../testing/test-policy.md#요구사항-출처)가 정한다.

## 섹션

아래 순서로 쓴다. 내용이 없는 섹션도 지우지 않고 `없음`으로 쓴다. 빠진 것인지 없는 것인지 구분하기 위해서다.

| 섹션 | 쓰는 것 |
| --- | --- |
| 출처 | 슬라이스, 라우트, 근거 Issue 번호. 챌린지는 과제 원문 위치 |
| 사용자 시나리오 | 사용자가 이 도메인에서 끝내야 하는 일. 행마다 출처 |
| 기능 요구사항 | ID, 요구사항, 출처 |
| 품질 요구사항 | Issue나 과제가 정한 측정 기준(성능, 접근성 등). 행마다 출처 |
| 범위 밖 | 이 도메인이 하지 않는 일. 행마다 출처 |

- 배경과 목표는 쓰지 않는다. Issue 본문의 문제에 있다.
- 완료 판정 기준 섹션은 두지 않는다. 요구사항은 [검증 문서](verification.md)에서 그 ID의 시나리오가 모두 기대 결과대로 통과하면 충족이다.

## 기능 요구사항

- 한 행에는 관찰 가능한 동작 하나만 쓴다. 테스트는 요구사항마다 대응하므로, 동작이 둘이면 한쪽만 확인해도 대응한 것처럼 보인다.
- 사용자가 보거나 조작한 결과로 쓴다. 컴포넌트, 상태, 함수 같은 구현 방식은 쓰지 않는다.
- 배치, 디자인 토큰, 움직임 값은 쓰지 않는다. 요구사항서 밖의 설계안에 둔다.
- 출처가 없는 요구사항은 쓰지 않는다. 필요하다고 판단되면 `(미결정)`으로 두고 사용자에게 묻는다.

## ID

- 형식은 `R-01`부터 두 자리 번호다. 도메인 안에서만 유일하다.
- 지운 ID는 다시 쓰지 않는다. PR `Test plan`의 대응이 다른 요구사항을 가리키게 된다.
- ID를 코드와 테스트에 쓰지 않는다. `.sdd/`는 저장소에 남지 않아 merge 뒤에는 가리킬 대상이 없다.
- PR `Test plan`에 대응을 쓸 때는 ID와 요구사항 문장을 함께 쓴다. ID만으로는 merge 뒤에 무엇을 확인했는지 알 수 없다.
