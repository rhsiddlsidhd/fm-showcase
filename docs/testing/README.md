# 테스트 전략

Frontend Mentor 챌린지를 TDD로 구현할 때의 테스트 전략이다. 이 README는 인덱스이자 공통 원칙이고, 층별 전략은 아래 문서에 둔다.

## 문서

| 문서 | 읽는 조건 | 다루는 내용 |
| ---- | --------- | ----------- |
| [`unit.md`](./unit.md) | 순수 함수, 훅, 개별 컴포넌트의 테스트를 쓸 때 | 단위 테스트의 대상, 도구, 작성 규칙 |
| [`integration.md`](./integration.md) | 페이지·기능 단위로 여러 조각을 묶어 검증하는 테스트를 쓸 때 | 통합 테스트의 경계, 라우터·네트워크 처리 |
| [`e2e.md`](./e2e.md) | 실제 브라우저로 사용자 흐름을 검증하는 테스트를 쓸 때 | E2E의 대상, 도구, 실행 위치 |

## 테스트 층

| 층 | 검증하는 것 | 실행 환경 | 도구 | 상태 |
| -- | ----------- | --------- | ---- | ---- |
| 단위 | 한 조각(함수, 훅, 컴포넌트)의 동작 | jsdom | Vitest, React Testing Library | 도입됨 |
| 통합 | 여러 조각을 묶은 화면·기능의 동작 | jsdom | Vitest, React Testing Library, user-event | 도입됨 |
| E2E | 빌드된 앱을 실제 브라우저로 사용 | 실제 브라우저 | Playwright | **미도입** |

- 비율은 단위 > 통합 > E2E 순으로 많이 둔다. 위 층일수록 느리고 깨지기 쉽다.
- 같은 동작을 여러 층에서 중복 검증하지 않는다. 가장 아래 층에서 확인할 수 있으면 거기서 끝낸다.
- 층을 가르는 기준은 파일 크기가 아니라 **무엇을 진짜로 쓰는가**다. 단위는 협력 대상을 대역으로 바꾸고, 통합은 화면 안의 조각을 진짜로 쓰고, E2E는 브라우저·라우터·빌드 결과물까지 진짜로 쓴다.

## TDD 순서

챌린지 하나의 구현은 바깥에서 안쪽으로, 실패하는 테스트를 먼저 쓰며 진행한다.

```
1. 챌린지 요구사항을 사용자 행동 문장으로 나눈다
2. 행동 하나당 통합 테스트 하나를 쓴다            → 실패 확인 (Red)
3. 통과시키는 최소 구현을 쓴다                    → 통과 확인 (Green)
4. 구현 안에서 로직이 생기면 단위 테스트를 먼저 쓴다 → Red → Green
5. 정리한다 (Refactor)                            → 테스트 전부 통과 유지
6. 챌린지가 끝나면 핵심 흐름만 E2E로 남긴다 (도입 후)
```

- Red 단계에서 **실패 이유가 맞는지** 확인한다. import 오류나 오타로 실패한 테스트는 Red가 아니다.
- 테스트를 통과시키려고 테스트를 고치지 않는다. 요구사항이 바뀐 경우에만 테스트를 고친다.
- 구현 없이 테스트만 통과하는 경우(테스트가 아무것도 검증하지 않음)를 막기 위해, 새 테스트는 구현 전에 한 번 실행해 실패를 본다.

## 공통 작성 규칙

| 항목 | 규칙 |
| ---- | ---- |
| 파일 위치 | 단위·통합은 대상 파일 옆에 둔다. `Foo.tsx` → `Foo.test.tsx` (현재 `scripts/git-hooks/message.test.ts`와 같다). E2E는 루트 `tests/`에 둔다 ([`e2e.md`](./e2e.md)) |
| 파일 이름 | 단위·통합은 `*.test.ts(x)`. E2E는 `*.spec.ts`로 구분한다 (Vitest가 E2E를 줍지 않도록) |
| 이름 | `describe`는 대상, `it`은 동작을 문장으로 쓴다. 구현 방식이 아니라 관찰 가능한 결과를 쓴다 |
| 구조 | Arrange → Act → Assert. 한 `it`에 하나의 동작 |
| 쿼리 우선순위 | `Role` > `LabelText` > `PlaceholderText` > `Text` > `DisplayValue` > `AltText` > `Title` > `TestId` 순으로 고른다 (RTL 공식 순서). `data-testid`는 다른 방법이 없을 때만 쓴다 |
| 쿼리 종류 | 있어야 하는 요소는 `getBy*`, **없음 확인은 `queryBy*`** (`not.toBeInTheDocument()`), 비동기로 나타나는 요소는 `findBy*` |
| `waitFor` | 안에는 단언만 넣고 부수 효과(클릭 등)를 넣지 않는다. 요소 하나를 기다릴 때는 `findBy*`를 쓴다 |
| 구현 의존 | state, 내부 함수 호출 횟수, CSS 클래스를 검증하지 않는다 |
| 독립성 | 테스트끼리 순서·상태를 공유하지 않는다. 전역 상태는 `afterEach`에서 되돌린다 |
| 시간·난수 | 가짜 타이머, 고정 시드로 통제한다. 실제 대기(`setTimeout`)를 쓰지 않는다 |
| 접근성 | 역할 기반 쿼리가 곧 접근성 검증이다. 쿼리가 안 잡히면 마크업을 고친다 (`jsx-a11y` 린트와 함께) |

## 강제와 안내

[프로젝트 README](../../README.md)의 구분을 따른다.

| 등급 | 규칙 | 판정 |
| ---- | ---- | ---- |
| 강제 | 모든 테스트가 통과한다 | CI의 `npm run test` |
| 강제 | 타입·린트·포맷·빌드가 통과한다 | CI의 `typecheck`, `lint`, `format:check`, `build` |
| 안내 | 테스트를 구현보다 먼저 쓴다 (Red 확인 포함) | `AGENTS.md` |
| 안내 | 층 배치가 맞다, 구현 세부가 아니라 행동을 검증한다 | 리뷰 |

- "테스트를 먼저 썼는가"와 테스트의 품질은 기계가 판정하지 못한다. 강제 항목은 통과 여부만 보장한다.
- 커버리지 수치 기준은 정하지 않았다. 아래 "미결정"을 본다.

## 실행

| 명령 | 용도 |
| ---- | ---- |
| `npm run test` | 전체 단위·통합 테스트를 한 번 실행 (`vitest run`). CI와 같다 |
| `npx vitest` | 감시 모드. 개발 중 Red/Green 반복에 쓴다 |
| `npx vitest run <경로>` | 특정 파일만 실행 |

- 테스트 파일이 하나도 없으면 `npm run test`는 `No test files found`로 실패한다.
- 설정은 `vite.config.ts`의 `test` 블록(jsdom, `globals: true`, `src/shared/test/setup.ts`)을 따른다. 공통 준비 코드는 `src/shared/test/`에 둔다 ([아키텍처](../architecture/segments.md)).

## 에이전트의 검증 분담 (안내)

같은 검증이 단계마다 2~4회 중복되지 않도록 역할마다 돌릴 것을 정한다.

| 역할 | 돌리는 검증 | 비고 |
| ---- | ----------- | ---- |
| test-engineer (Red) | `npm run test -- <새 테스트 파일>` 1회 | 0이 아닌 종료 코드와 실패 메시지 원문을 보고한다 |
| executor (Green) | `npm run test -- <새 테스트 파일>`, `npm run test`, `npm run typecheck` | 린트·포맷·빌드는 verifier가 한다 |
| verifier | 위 5종을 각각 1회 | 앞선 verifier의 결론은 읽지 않는다. 독립 판정을 위해서다 |
| 메인 세션 | 원칙적으로 재실행하지 않고 CI 결과와 에이전트 보고를 대조한다 | CI 결과가 없거나 보고가 의심되면 직접 재실행한다 |

- 에이전트의 보고는 그대로 믿지 않는다. 보고의 실행 결과는 CI 결과나 출력 원문과 대조한다.

## 미결정

| 항목 | 현재 | 결정이 필요한 시점 |
| ---- | ---- | ------------------ |
| E2E 도구 도입 | Playwright를 제안하나 설치하지 않았다 | 첫 챌린지의 통합 테스트가 통과한 뒤 |
| E2E의 CI 실행 | 없음 | E2E 도입과 함께 |
| 네트워크 대역 도구 | 없음 (`vi.stubGlobal('fetch')` 수준) | API를 부르는 챌린지를 처음 만들 때 |
| 커버리지 기준 | 측정하지 않는다 | 챌린지 여러 개가 쌓인 뒤 |
| 시각 회귀 테스트 | 하지 않는다 | 디자인 일치 검증을 자동화하고 싶을 때 |
