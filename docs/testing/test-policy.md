# 테스트 정책

모든 층의 테스트에 공통으로 적용하는 기준을 정한다. 층마다 무엇을 검증하는지는 [`test-boundaries.md`](./test-boundaries.md)에 있다.

## 요구사항 출처

- 요구사항의 권위 출처는 Issue다. 챌린지는 과제 원문도 포함한다.
- `.sdd/`의 설계 문서는 구현용 작업본이다. 저장소에 남지 않아 완료 판정의 근거가 되지 못한다.
- 요구사항과 테스트의 대응은 PR `Test plan`에 남긴다.

## 테스트 선행

- [커밋 순서](../git/commit.md#테스트-선행-증거)는 구현보다 테스트를 먼저 썼다는 증거를 남긴다.
- 테스트 커밋 전에 기능이 없어서 실패하는 것을 확인한다.
- 버그 수정과 기존 동작 변경도 테스트가 먼저다.
- 동작이 바뀌지 않는 변경(리팩터링, 문서, 설정, CI)은 예외다.
- 사용자 동작이 바뀌지 않는 시각적 조정이나 문서 변경은 예외다. 시각적 요구사항은 적절한 브라우저 검증이나 사람 확인으로 다룬다.
- 예외는 Issue 라벨이나 커밋 접두사가 아니라 동작이 바뀌는지로 판정한다. 라벨이 `refactor`여도 동작이 바뀔 수 있다.

## 테스트 대상 선정 기준

- 요구사항이 정한 관찰 가능한 동작을 테스트한다.
- 요구사항에 없는 구현 세부는 테스트하지 않는다.

## 층별 검증

- 같은 사용자 동작을 여러 층에서 검증할 수 있다. 각 테스트가 서로 다른 실패를 잡는지 확인하고, 같은 주장만 반복하는 테스트는 줄인다.
- Unit에서 확인한 로직도 UI 연결이 중요하면 Integration에서 대표 경로를 확인한다. 중요한 사용자 흐름은 E2E에서 빌드 결과와 브라우저 동작을 확인한다.

## 작성 규칙

- 기대값은 요구사항이나 계산 예시처럼 구현 밖의 출처에서 가져온다. 구현 결과를 복사한 테스트는 구현이 틀려도 통과한다.
- 쿼리는 역할과 접근 가능한 이름을 먼저 쓴다. `getByTestId`는 다른 방법이 없을 때만 쓴다.
- 테스트 이름은 구현보다 관찰 가능한 결과를 명확하게 설명한다.

## 완료 기준

- 요구사항마다 적절한 검증 방법이 있다. 자동화가 적합하지 않으면 사람 확인과 그 근거를 남긴다.
- 요구사항에 포함되고 실제 도달 가능한 오류, 빈 상태, 로딩 상태를 검증한다.
