# 테스트 정책

모든 층의 테스트에 공통으로 적용하는 기준을 정한다. 층마다 무엇을 검증하는지는 [`test-boundaries.md`](./test-boundaries.md)에 있다.

## 요구사항 출처

- 요구사항의 권위 출처는 Issue다. 챌린지는 과제 원문도 포함한다.
- `.sdd/`의 설계 문서는 구현용 작업본이다. 저장소에 남지 않아 완료 판정의 근거가 되지 못한다.
- 요구사항과 테스트의 대응은 PR `Test plan`에 남긴다.

## 테스트 선행

[증거](../../README.md#증거)의 커밋 순서가 이 규칙을 받친다.

- 요구사항 하나마다 테스트 커밋을 먼저, 구현 커밋을 그다음에 만든다.
- 테스트 커밋 전에 기능이 없어서 실패하는 것을 확인한다.
- 구현 커밋까지 만든 뒤에 push한다. CI는 push된 최신 커밋을 검증한다.
- 버그 수정과 기존 동작 변경도 테스트가 먼저다.
- 동작이 바뀌지 않는 변경(리팩터링, 문서, 설정, CI)은 예외다.
- [`테스트하지 않는 것`](./test-boundaries.md#테스트하지-않는-것)에만 해당하는 변경은 예외다.
- 예외는 Issue 라벨이나 커밋 접두사가 아니라 동작이 바뀌는지로 판정한다. 라벨이 `refactor`여도 동작이 바뀔 수 있다.

## 테스트 대상 선정 기준

- 요구사항이 정한 관찰 가능한 동작을 테스트한다.
- 요구사항에 없는 구현 세부는 테스트하지 않는다.

## 중복 검증 금지

- 같은 동작은 한 층에서만 검증한다.
- 가장 아래 층에서 확인할 수 있으면 거기서 끝낸다.
- 아래는 겹쳐도 둔다.
  - 로직을 `lib/`·`model/`로 내린 뒤에도 그 로직을 쓰는 동작 컴포넌트의 테스트는 대표 경로 하나를 확인한다. 연결이 맞는지는 Unit이 잡지 못한다.
  - E2E의 대표 흐름은 하위 층과 겹쳐도 둔다. 확인하는 것은 동작이 아니라 빌드 산출물이다 ([E2E 경계](./test-boundaries.md#e2e-경계)).
  - [의존성 격리 원칙](./test-boundaries.md#의존성-격리-원칙)이 정한 E2E 재확인.

## 작성 규칙

- 기대값은 요구사항이나 계산 예시처럼 구현 밖의 출처에서 가져온다. 구현 결과를 복사한 테스트는 구현이 틀려도 통과한다.
- 쿼리는 역할과 접근 가능한 이름을 먼저 쓴다. `getByTestId`는 다른 방법이 없을 때만 쓴다.
- 테스트 이름은 구현이 아니라 사용자가 관찰하는 동작을 한국어 문장으로 쓴다.

## 완료 기준

- 요구사항마다 대응하는 테스트가 있다.
- [`테스트하지 않는 것`](./test-boundaries.md#테스트하지-않는-것)에만 해당하는 요구사항은 이 저장소의 예외로, 테스트가 없어도 완료로 본다.
- 해당 슬라이스에 있는 오류, 빈 상태, 로딩 상태를 모두 검증한다.
