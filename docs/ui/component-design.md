# 컴포넌트 설계 원칙

컴포넌트 설계는 책임, 상태의 소유권, 컴포넌트 사이의 의존성을 명확히 하는 일이다. 이 문서는 각 원칙이 무엇을 지키려는 것인지, 어떤 형태로 어긋나는지, 언제 서로 충돌하는지를 적어 설계 판단의 근거를 준다. 코드를 어디에 둘지는 [레이어](../architecture/layers.md)와 [세그먼트](../architecture/segments.md)가 정한다.

하나의 설계 결정은 세 축에서 읽는다. 책임이 하나인가, 각 사실의 소유자가 하나인가, 컴포넌트가 상대의 내부를 얼마나 아는가.

## 책임

> Gather together the things that change for the same reasons. Separate those things that change for different reasons.
>
> — Robert C. Martin, The Single Responsibility Principle

단일 책임 원칙과 관심사 분리가 지키려는 것은 변경의 범위다. 요구 하나가 바뀔 때 한 곳만 고치면 되고, 한 가지를 이해하려고 다른 것까지 읽지 않아도 된다.

변경 이유는 코드를 고치게 만드는 요구의 출처다. 화면의 구성이나 모양이 바뀌는 것, 사건에 따라 상태가 바뀌는 규칙이 바뀌는 것, 요청 방식이나 시점이 바뀌는 것은 서로 다른 출처다. 한 컴포넌트가 이 중 둘 이상을 이유로 고쳐진다면 책임이 섞인 것이다.

책임이 섞였는지 가늠하는 질문:
- 이 컴포넌트를 고치게 만드는 서로 다른 이유가 몇 가지인가?
- 화면 없이 입력과 상태만으로 설명하고 검증할 수 있는 규칙이 컴포넌트 안에 들어 있는가?
- 외부 사건이 도착하는 순서에 따라 결과가 달라지는 코드가 컴포넌트 안에 있는가?

분리에도 비용이 있다. 책임이 하나뿐인 코드를 나누면 읽을 때 오가야 할 파일만 늘어난다. 같은 이유로 바뀌는 것은 함께 두는 것이 원칙의 앞 절반이다. 분리로 얻는 것(한 요구가 한 곳만 바꾼다)이 읽는 비용보다 큰지로 판단한다.

컴포넌트가 자기 화면의 일시적인 상태(패널이 열렸는지, 입력 중인 값)를 갖는 것은 표시 책임의 일부다. 이 상태는 변경 이유가 화면과 같으므로 분리할 대상이 아니다.

## 상태의 소유권

같은 사실은 한 곳이 소유하고, 나머지는 그것을 받아 쓴다. 기준이 둘이면 서로 다른 말을 할 수 있고, 그 어긋남이 버그의 근원이 된다. 화면은 상태의 결과여야 하며, 화면에 보이는 값을 따로 저장하면 기준이 둘이 된다.

> If you can calculate some information from the component's props or its existing state variables during rendering, you should not put that information into that component's state.
>
> — React, Choosing the State Structure

기준이 둘이 되는 흔한 형태:
- 상태에서 계산할 수 있는 값을 따로 저장한다.
- 함께 참이 될 수 없는 값을 따로 저장한다. 하나의 상태 값이 가질 수 있는 종류로 합치면 모순이 생길 자리가 없어진다.
- 상태의 종류를 문자열 값 비교로 구분한다. 오타나 새 값이 타입에 걸리지 않는다.
- 부모가 자식의 진행 단계를 이벤트로 받아 같은 단계를 다시 만든다. 단계의 기준이 부모와 자식 두 곳이 된다.
- 렌더에 보이지 않는 값으로 사건 사이를 조율한다. 상태의 일부가 렌더 밖에 숨어서 읽는 사람이 전체 상태를 알 수 없다.

소유 위치는 그 사실을 읽는 컴포넌트에 가까울수록 좋다. 둘 이상의 컴포넌트가 같은 사실을 필요로 할 때만 공통 소유자로 올린다. 필요 없이 올리면 읽지 않는 컴포넌트까지 그 상태에 영향을 받는다.

같은 사건으로 함께 바뀌는 상태와 그 전이 규칙은 한 곳에 모은다(높은 응집도). 흩어져 있으면 사건을 하나 추가할 때 고칠 곳을 빠뜨린다.

> Components with many state updates spread across many event handlers can get overwhelming. For these cases, you can consolidate all the state update logic outside your component in a single function, called a reducer.
>
> — React, Extracting State Logic into a Reducer

모으는 방식에는 비용이 있다. React 문서는 상태 갱신이 단순하면 `useState`가 읽기 쉽고 코드도 적다고 인정한다. 갱신이 복잡해질 때 갱신이 "어떻게 바뀌는가"와 "무슨 일이 일어났는가"를 나눌 수 있다는 것이 모으는 쪽의 이득이다. 전이 규칙이 순수 함수가 되면 컴포넌트와 따로 검증할 수 있다. 판단은 전이의 복잡도가 이 이득을 살 만큼 되는지로 한다.

## 의존성

컴포넌트가 상대의 내부를 아는 만큼이 결합이다. 결합이 좁으면 한쪽의 내부가 바뀌어도 다른 쪽이 깨지지 않는다(낮은 결합도, 캡슐화).

결합이 넓어지는 신호는 부모가 자식의 내부 단계를 알아야 하는 경우다. 자식이 단계마다 부모에게 따로 알리면, 부모는 자식의 단계 구성에 의존한다.

사건을 하나의 타입으로 모으면 결합 면이 좁아진다. 다만 그 타입이 둘 사이의 공유 계약이 되어, 바꿀 때 양쪽을 함께 고쳐야 한다. 자식이 입력값 하나를 알리는 것처럼 사건이 독립적이고 하나뿐이면 모을 대상이 없다. 서로 무관한 사건을 억지로 하나의 타입으로 묶으면 오히려 결합이 늘어난다.

## 원칙이 충돌할 때

- 응집도와 결합도: 흩어진 규칙을 한 곳에 모으면 응집은 오르지만, 그곳이 여러 컴포넌트가 의존하는 지점이 된다. 모으는 이득이 그 의존의 비용보다 큰지 본다.
- 책임 분리와 단순함: 분리는 파일과 간접 계층을 늘린다. 책임이 섞여서 생기는 고통(변경이 여러 곳에 번지는 것, 규칙을 화면 없이 검증할 수 없는 것)이 실제로 있을 때 분리한다.
- 소유 위치의 근접성과 단일 기준: 가까이 두면 영향 범위가 좁고, 올리면 기준이 하나로 유지된다. 둘 이상이 같은 사실을 필요로 하는지가 기준이다.
