# UI 규칙

모든 도메인이 화면을 설계하고 구현할 때 따르는 규칙을 둔다. 도메인의 정의와 설계안 공통 규칙은 [`spec/`](../spec/README.md)에 있다.

## 판단 기준

- 도메인마다 디자인 기준이 달라 사이트 공통 디자인 기준을 두지 않는다. 공통으로 두는 것은 설계안 작성 규칙과 구현 규칙이다.
- 항상 알아야 할 공통 내용은 이 README에, 조건부 공통 규칙은 주제별 문서에, 도메인마다 달라지는 내용은 도메인 설계안에 둔다.
- 설계안은 무엇을 어디에 어떻게 만들지 쓴다.
- 챌린지 화면에는 쇼케이스 공통 요소를 두지 않는다. 원본 재현이 챌린지의 목적이기 때문이다.

| 도메인 종류     | 라우트        | 디자인 기준                  |
| --------------- | ------------- | ---------------------------- |
| 쇼케이스 페이지 | `/`           | 직접 정한다                  |
| 챌린지 페이지   | `/<슬라이스>` | 과제와 원본 디자인을 분석한다 |

## 산출 위치

설계 단계의 `theme.css`는 설계안과 같은 디렉토리에 둔다([산출 위치](../spec/README.md#산출-위치)).

- 원본 디자인 파일은 두지 않는다. 분석한 설계안만 둔다.
- 구현 세션은 도메인의 첫 구현에서 `theme.css`를 슬라이스로 복사한다. 이후 기준은 `src/`의 파일이다.

## 작성 규칙

- 디자인 토큰의 값은 `theme.css`에만 둔다. 설계와 구현이 같은 내용이라 문서로 쓰지 않는다.
- 구현은 `theme.css`가 준비된 뒤에 시작한다. 나머지 시작 조건은 [작성 규칙](../spec/README.md#작성-규칙)에 있다.
- 컴포넌트를 직접 만든 사유는 PR 본문에 쓰지 않아도 된다.
- 챌린지는 PR merge 전에 사용자가 원본과 화면을 비교하고 결과를 PR Test plan에 남긴다. 시각 일치는 테스트로 검증하지 않기 때문이다.
