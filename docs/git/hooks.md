# 훅 규칙

로컬 git 훅과 CI가 각각 무엇을 판정하는지와 그 이유를 둔다. 판정 로직은 [`.githooks/`](../../.githooks)에, 실행하는 검사 목록은 그 코드와 [`package.json`](../../package.json) scripts, [`ci.yml`](../../.github/workflows/ci.yml)에 있다.

## 층별 책임

뒤 단계로 갈수록 판정하는 범위가 커진다. 앞 단계가 판정한 것은 뒤 단계가 다시 판정해도 되지만, 뒤 단계의 책임을 앞 단계로 당기지 않는다.

| 단계       | 판정하는 질문                                  | 판정 범위                                   |
| ---------- | ---------------------------------------------- | ------------------------------------------- |
| pre-commit | 지금 이 위치에서 커밋해도 되는가               | `main` 직접 커밋, 브랜치 이름               |
| commit-msg | 메시지가 형식을 지키는가                       | 제목 형식                                   |
| pre-push   | 이 커밋들을 이 원격 ref로 내보내도 되는가      | 목적지(`main` 보호, 원격 브랜치 이름)와 코드 품질. 테스트는 변경 관련만 |
| CI         | merge해도 되는가                               | 빌드와 E2E를 포함한 전체 검사               |

## pre-push가 품질을 맡는 이유

- 커밋 단계에서는 품질을 검사하지 않는다. [테스트 선행](./commit.md#테스트-선행-증거)은 실패하는 테스트만 담은 커밋을 먼저 남겨야 하는데, 커밋 단계에서 테스트를 돌리면 그 커밋을 만들 수 없다.
- push는 구현 커밋까지 만든 뒤에 하므로 이 시점에는 검사가 통과해야 한다. push 전에 잡으면 CI 왕복을 기다리지 않고 실패를 고칠 수 있다.
- 빌드와 E2E는 pre-push에서 돌리지 않는다. 시간이 오래 걸리고 브라우저 설치가 필요하다. merge 판정에만 필요하므로 CI가 맡는다.
- 원격 브랜치를 지우거나 태그만 push할 때는 새 커밋을 내보내지 않으므로 품질 검사를 건너뛴다.
- 검사를 끄는 환경 변수 같은 우회 경로는 두지 않는다. 우회가 필요해 보이면 실패 원인을 고친다.

## pre-push가 변경 관련 테스트만 돌리는 이유

- CI는 PR마다 전체 테스트를 돌린다. pre-push도 전체를 돌리면 두 층이 같은 실패만 잡고 push마다 기다림만 늘어난다. [층별 검증](../testing/test-policy.md#층별-검증)처럼 두 층이 서로 다른 실패를 잡게 나눈다.
- pre-push는 "이 브랜치의 변경이 기존 테스트를 깨는가"를 묻는다. 바뀐 파일과 import 그래프로 이어진 테스트만 돌린다. 방금 쓴 구현이 자기 테스트나 이웃 테스트를 깨는 가장 흔한 실패는 여기서 잡힌다.
- CI는 "merge 결과 전체가 통과하는가"를 묻는다. 관련 테스트 판정이 놓친 의존, `main`의 다른 변경과의 상호작용, 훅을 거치지 않은 변경은 CI의 전체 테스트가 잡는다.
- 그래서 pre-push 통과는 merge 허가가 아니다. merge는 CI가 판정한다.

### 전체 테스트로 승격하는 기준

- 테스트가 import 그래프로 추적되지 않는 방식으로 파일에 의존하면, 그 파일이 바뀌어도 관련 테스트가 0개로 나온다. 서브프로세스로 실행하는 코드, fs로 읽는 파일, 파일 목록만 쓰는 `import.meta.glob`, 의존성 잠금 파일이 그렇다. 이런 경로가 바뀌면 전체 테스트로 승격한다.
- 승격 목록은 [`vite.config.ts`](../../vite.config.ts)의 `test.forceRerunTriggers`에 있다. 훅에는 경로를 판정하는 코드를 따로 두지 않는다.
- 패턴은 바뀐 파일의 절대 경로와 대조되므로 `**/`로 시작해야 한다. 접두가 없으면 오류 없이 승격이 꺼진다. 목록은 vitest 기본값을 펼친 뒤 더한다. 펼치지 않으면 기본값(`package.json`, vite·vitest 설정)이 빠진다.
- 새 테스트를 쓸 때 목록에 더할지는 [작성 규칙](../testing/test-policy.md#작성-규칙)으로 판단한다.

### 한계

- 비교 기준은 PR의 base가 아니라 `refs/remotes/origin/main`과의 merge-base다. Issue 브랜치로 향하는 작업 브랜치도 `main` 기준으로 고른다. 로컬의 `origin/main`이 오래됐으면 비교 범위가 넓어져 테스트를 더 돌린다.
- 로컬에 `origin/main`이 없으면 vitest가 git 오류로 끝나 push가 거부된다. `git fetch origin main`으로 받은 뒤 push한다.
- 관련 테스트가 0개면 실패 없이 끝나 push가 진행된다. 예를 들어 문서만 바꾼 push다.
- 트리거 경로 안의 파일을 트리거 밖으로 옮기면(rename) 승격되지 않을 수 있다. git이 옮긴 뒤의 경로만 변경으로 보고하기 때문이다. 이 경우는 CI가 잡는다.
- watch 모드에서도 트리거 경로가 바뀌면 전체 테스트를 다시 돌린다.
- 패턴이 `**/`로 시작하므로 저장소의 상위 경로나 저장소 안의 같은 이름 디렉토리(예: 다른 위치의 `public`)도 승격된다. 테스트를 더 돌리는 쪽이라 그대로 둔다.

## CI의 한계

- CI 실행은 건너뛸 수 없다. `main` 보호가 CI 통과를 필수로 요구한다.
- 하지만 검사 정의는 같은 PR이 바꿀 수 있다. [`ci.yml`](../../.github/workflows/ci.yml), [`package.json`](../../package.json) scripts, `vite.config.ts`의 `test` 설정, [`.githooks/`](../../.githooks)가 그렇다. 이 파일을 바꾸는 PR은 리뷰가 검사를 약화하지 않는지 확인한다.

## 신뢰 범위

- 훅은 체크아웃한 브랜치의 `.githooks/` 코드와 `package.json` scripts를 실행한다. 신뢰하지 않는 브랜치에서 커밋하거나 push하면 그 브랜치의 코드가 내 환경에서 실행된다.
- 신뢰하지 않는 브랜치는 이 작업 저장소와 격리된 별도 clone에서 다룬다. 훅을 끄거나 건너뛰는 방식으로 다루지 않는다.

## 작업 트리를 검사 대상과 맞추는 이유

품질 검사는 push되는 커밋이 아니라 지금 작업 트리에서 돈다. 둘이 다르면 검사가 통과해도 push되는 커밋의 품질을 보장하지 못하므로, 다음 경우는 검사 전에 거부한다.

- 작업 트리에 커밋하지 않은 변경이 있으면 거부한다. ignore되지 않은 새 파일도 포함한다. 커밋되지 않은 수정이 검사를 통과시키거나 실패시킬 수 있다. 커밋하거나 stash한 뒤 push한다.
- push하는 브랜치가 지금 체크아웃한 커밋과 다르면 거부한다. 예를 들어 다른 브랜치를 체크아웃한 채 그 브랜치를 push하면 검사는 엉뚱한 코드를 본다. 그 브랜치를 체크아웃한 상태에서 push한다.
