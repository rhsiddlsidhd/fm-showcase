# FM Showcase

AI가 작성한 코드를 신뢰할 근거를 구조로 갖추는 프로젝트. Frontend Mentor 챌린지 구현 결과물을 모은 쇼케이스를 그 수단으로 만든다.

## 현재 상태

| 항목                                                                           | 상태                                                                         |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 앱 골격 (Vite, React, TypeScript, Tailwind, shadcn/ui, React Router)           | 구현됨. 화면은 제목 하나뿐이다                                               |
| 쇼케이스 사이트 (챌린지 목록·상세)                                             | 설계만 있음                                                                  |
| CI (`verify`: typecheck, lint, lint:fsd, format:check, test, build)            | 구현됨                                                                       |
| `main` 보호 (PR 필수, `verify` 통과 필수), merge commit만 허용                 | 적용됨                                                                       |
| 로컬 git 훅 (커밋 메시지·이름 규칙과 AI 관여 선언, `main` 직접 커밋·push 차단) | 구현됨                                                                       |
| 에이전트 안내 (`AGENTS.md`)                                                    | 문서 인덱스(Context)만 있음                                                  |
| 테스트                                                                         | 단위 테스트만 있다. 통합·E2E는 전략 문서만 있고 E2E는 도구를 도입하지 않았다 |
| 디렉토리 구조 (FSD, Steiger 검사)                                              | `src/`를 `app`/`shared`로 이전했다. `verify`가 Steiger를 돌린다              |
| 같은 PR에서 3회 연속 실패하면 루프를 멈추는 제어                               | 미구현                                                                       |
| 증거 모델                                                                      | 정의함([증거](#증거)). 일부 증거는 아직 없다. 검증 로그 훅은 폐기했다        |

## 목표

OMC(oh-my-claudecode, Claude Code용 플러그인)를 만들지 않고 가져다 쓰되, 그 위에 결정론적 구조를 얹어 AI의 비결정성을 통제하고, 통제가 작동했다는 근거를 저장소에 남긴다.

- 증명하는 것은 AI 도구를 만드는 능력이 아니라, 외부 도구를 가져와 의도대로 통제하는 능력이다.
- 쇼케이스 사이트는 그 통제 아래 만든 **수단이자 결과물**이다.

## 접근 방식

OMC는 외부 도구이며, 이 프로젝트의 작업물은 그 위에 얹는 결정론적 구조다. 첫 적용 사례는 TDD다. OMC의 `tdd`는 프롬프트 수준이라 비결정적이므로, 테스트 작성을 LLM 바깥의 코드로 강제한다.

### 기준과 검증

확률적 모델의 비결정성과 판단의 불확실성을 통제하기 위해, 기계가 판정하는 기준은 설정과 검증 코드(테스트, 훅)로 고정해 CI가 결정론적으로 강제하고, 의미 판단이 필요한 기준은 문서에 이유와 함께 명시해 판단의 범위를 좁힌다.

| 구분      | 담는 것                                                  | 판정                                                                                                  |
| --------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 설정      | 기계가 읽는 기준. 설정 파일과 저장소 설정(GitHub)        | 도구가 참/거짓을 판정한다. CI가 실행하고, 실패하면 merge를 차단한다                                   |
| 검증 코드 | 판정 로직 자체. 테스트와 로컬 git 훅                     | 테스트는 CI가 실행한다. 훅은 로컬에서 먼저 막는다                                                     |
| 문서      | 의미 판단이 필요한 기준. 이유, 예외, 판단 기준 (`docs/`) | 리뷰가 확인한다. 에이전트가 따르기를 기대하는 비결정 규칙이다 ([리뷰 기준](docs/README.md#리뷰-기준)) |

- 기계로 판정되게 만들 수 있는 기준은 문서에 두지 않고 설정이나 검증 코드로 올린다. 문서는 아직 올리지 못한 기준과 올릴 수 없는 판단이다.
- 설정과 검증 코드는 기준의 충족 여부만 보장하며, 테스트의 품질처럼 의미 판단이 필요한 영역은 보장하지 않는다.
- 문서의 기준은 판단의 범위를 좁힐 뿐 결정론적이지 않다.

### 파이프라인

```
로컬 개발 (에이전트 작업) → push, PR → CI 독립 실행
                                        ├ 통과 → merge 가능
                                        └ 실패 → merge 차단 → 실패 로그를 로컬로 가져옴
                                                            → 로컬에서 수정
                                                            → 같은 PR에 push → CI 재실행
```

- CI가 최종 권위다. 로컬 훅은 조기 피드백용이다.
- 같은 PR에서 3회 연속 실패하면 루프를 멈추고 사람에게 넘긴다. 멈춘 사실도 기록한다.

### 증거

증거는 주장을 받치는 개별 산출물이다. 브라우저 UI가 아니라 저장소와 GitHub에 남긴다. 구현된 것과 아닌 것은 상태 열에서 구분한다.

| 주장                              | 증거                                                                       | 만드는 주체                           | 상태                                                                |
| --------------------------------- | -------------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------- |
| 병합된 코드는 검증을 통과했다     | CI(`verify`) 실행 결과. 커밋 SHA에 결속되고, `main` 보호가 통과를 강제한다 | GitHub Actions (결정론)               | 있음                                                                |
| 테스트를 구현보다 먼저 썼다       | 작업 브랜치의 커밋 순서(테스트 → 구현)와 그 이력의 보존(merge commit)      | git (결정론)                          | 이력 보존만 있음. 순서를 CI가 재현해 확인하지는 않는다              |
| AI와 사람의 기여가 구분된다       | 커밋의 `Co-Authored-By` 또는 `AI-Assisted: none` 트레일러                  | 커밋 작성 시 표기                     | `commit-msg` 훅이 선언을 강제한다. 자기 선언이라 위조는 막지 못한다 |
| AI의 오류를 사람이 걸러냈다       | 오류·교정 사례 (주장 ↔ 실제 결과 ↔ 발견 방법 ↔ 조치)                       | 사람이 작성하고 원본 실행 결과를 링크 | 없음                                                                |
| 설계 결정의 이유를 설명할 수 있다 | 결정 기록                                                                  | 사람이 작성                           | 없음. 이유가 문서마다 흩어져 있다                                   |

- 증거는 신뢰를 증명하지 않고 판단의 근거를 준다. CI 통과는 테스트의 품질을 보장하지 않는다.
- 사람이 쓰는 증거는 결정론적이지 않다. 원본 실행 결과를 링크해 확인할 수 있게 한다.
- 한계: 차단이 한 번도 없었던 챌린지는 통과 기록만 남는다.
- 증거가 외부 기준에 답하는지는 [면접 문항지](docs/assurance/questions.md)와 [문항 대응표](docs/assurance/answers.md)로 채점한다. 문항지는 목표가 아니라 채점표다.

## 사이트 소개

Frontend Mentor 챌린지 구현물의 목록·상세 쇼케이스.

- 챌린지 카드 목록과 필터(난이도, 사용 기술 등)
- 챌린지 상세: 설명, 구현 스택, 라이브 링크, 저장소 링크, 증거 문서 링크

사이트는 증거를 보여주는 뷰어가 아니라 증거 문서로 가는 진입점이다.

## 시작하기

```bash
nvm use    # .nvmrc: 24.17.0
npm ci
npm run dev
```

`npm ci`가 끝나면 `prepare` 스크립트가 `core.hooksPath`를 `scripts/git-hooks`로 설정한다.

### 스크립트

| 명령                   | 용도                                                                           |
| ---------------------- | ------------------------------------------------------------------------------ |
| `npm run dev`          | 개발 서버                                                                      |
| `npm run build`        | 타입 검사 후 프로덕션 빌드                                                     |
| `npm run preview`      | 빌드 결과 미리 보기                                                            |
| `npm run test`         | 테스트를 한 번 실행. 실행 방법은 [테스트 전략](docs/testing/README.md)을 본다  |
| `npm run typecheck`    | 앱과 스크립트의 타입 검사                                                      |
| `npm run lint`         | ESLint                                                                         |
| `npm run lint:fsd`     | Steiger. FSD 디렉토리 구조 검사 ([아키텍처](docs/architecture/enforcement.md)) |
| `npm run format`       | Prettier로 파일을 고친다                                                       |
| `npm run format:check` | Prettier 검사. 파일을 고치지 않는다 (CI가 쓴다)                                |
